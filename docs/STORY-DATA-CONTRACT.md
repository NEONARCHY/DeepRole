## RP224 Memory lifecycle

StoryFact adds optional task {key,title,status:open|completed|cancelled}; exact task keys identify separate obligations. Open records require promise/plan/task; terminal records require event. New open titles must be literal source clauses. Unknown terminal linkage, renamed tasks and reopening are review-only. Explicit progress is claim.transition:progress; correction and differing state values without progress require review. Legacy stored facts remain valid.

Human review may add replaces containing exact storyFactIdentity strings for at most eight comparable current game facts. Model inline/batch parsers reject replaces. Resolver checks selected head, writer, current game revision, pending origin and offered keys under the repository lock. compactStoryFacts folds selected events chronologically, removes explicitly superseded memory and retains latest task/claim slots. Historical sources remain; baseline/shared-game facts carry the same folded state across checkpoint/continuation/reset/backup.

Review reads expose bounded old/new comparisons with quotes. Context and batch hints omit replaces and quotes; task keys/titles/status remain. Context still selects at most eight facts within its supplied token budget; task priority does not increase that budget. Earlier task changes cannot replace a later known task state during batch backfill. Protected author text and existing native dispatch/source guards remain intact. Model-supplied semantic keys and risk are not independent proof of interpretation.

Позиция продвигается только после полного names/more envelope с совпадающим requestId, до 32 имён и непрерывными цитатами; имя должно буквально присутствовать в цитате. Пустое names при more=false допустимо, more=true без новых имён останавливается. Каталог не доказывает полноту состава или разрешение одноимённых людей. Данные модели не становятся командами базе.

Profiles использует по одному устойчивому ключу/буквальному имени из каталога, его исходные цитаты и недавние окна вокруг точного имени: до 16 источников / 12000 символов JSON. Весь пакет явно вложен в запрос нового чата; зависимость от памяти предыдущего окна отсутствует. Возвращается прежняя полная CastMember-схема с проверяемыми оценками, возраст не придумывается. Алиасы здесь пустые, present/partners обязательны пустые: актуальная физическая сцена не выводится из ограниченных старых выдержек. Цитаты проверяются сначала только против реально переданных окон, затем ID окон заменяется исходным ID записи для review/apply. Механическое включение цитаты не доказывает смысл — финальная проверка пользователя сохранена.

Каждый успешно подготовленный шаг временно ready с large.stage не done. Worker выходит в прежний owned cleanup; только подтверждённое удаление чата и фактическое закрытие его вкладки запускают следующую независимую работу с новым CastJob и service ID. Source signature, cursor, каталог и валидные анкеты переносятся локально; ownership и журнал не содержат лор/имена/промпты. В audit result означает результат этого служебного шага, не подтверждение полноты всего мира. Новая native операция имеет собственную привязку workerChatId, прежняя не переназначается другому чату.

Смена страницы после cleanup, отказ очистки, cancel, vault, purged world и поздний старый worker блокируют продолжение. Перезагрузка/разблокировка/status не авторизуют повторную отправку; resume явный и пропускает завершённое. Подпись сверяется под lock при приёме и перед созданием следующего шага. Изменившийся источник требует явного restart без переноса старых предложений. Скрытие статуса и private-window режим сохраняются между шагами. Завершённые профили из частичного checkpoint можно сохранить для проверки без повторного запроса этого имени.

Задание хранится в прежней локальной cast-таблице и сейфе, но по прежнему backup-контракту исключается из переносных копий. Backup сохраняет записанный лор/персонажей и безопасную историю service, не право продолжить native job. Семантический поиск, гарантированная полнота, разрешение двойников и производительность огромной библиотеки этим не заявляются.

## Очередь найденных анкет RP-03 211

`DR_CHARACTER_DISCOVERY/queue` получает scope/guard, operation enqueue/resume/clear и не более 20 явных eventId/name/values одного транспортного запроса. Размер страницы не ограничивает общий каталог или сохранённую очередь. Имена проверяются против текущей библиотеки/очереди; неизвестный или уже добавленный/отклонённый кандидат не ставится в работу. Готовая анкета текущего head не перегенерируется. Черновики не становятся entity или каноном.

Необязательное `StoryEvent.characterProfileTask` хранит непрозрачный id, точный guard, имя, четыре исходных авторских значения, pending/preparing/ready/failed и requestId. Граф требует допустимый завершённый head той же ветки и принадлежность исходной цитаты его предкам. Claim under repository lock переводит только совпадающее pending в preparing; повторный claim отклоняется. Применение проверенного `DiscoveryProfile` требует совпадения queueId и текущего requestId, одновременно сохраняет proposal и ready. Ошибка меняет только своё preparing, не готовый результат и не новую попытку.

Content runner обслуживает по одной анкете и ждёт успешного окончания cleanup/ack прежнего field-worker. Он не повторяет failed сам и не начинает новый job после неясной/неудачной очистки. Queue edit проходит сериализованный field coordinator: активные owners блокируют изменения, утраченные jobs сперва отменяются и пробуждают собственный worker для cleanup. Ownership не содержит имени/черновика/источников; они остаются в защищённом story record. Vault/backup v4 сохраняют очередь, но старый строгий reader может не принять новое поле.

После stop/reload/закрытия панели продолжение требует явного resume. Никаких модельных запросов при чтении результатов или восстановлении backup нет. Resume не запускает ready и не переносит старый guard в новый head: при смене истории надо очистить очередь и выбрать актуальные имена снова. Clear удаляет метаданные работы, оставляет profiles/proofs; поздний старый ответ после clear отклоняется. Ручная подготовка вне очереди сохраняет прежнее поведение и снимает метку задания после успешного результата. Предложения по-прежнему требуют выбранных полей и явного добавления; новые люди, сцена, числа и изображения автоматически не записываются.

Переполнение отклоняется без обрезки и частичной записи. Not-found/conflict выбрать нельзя. Изменившиеся с подготовки поля пропускаются; независимые пригодные дополнения можно принять. Смена head отклоняет устаревшее подтверждение. Commit guard проверяет страницу и vault/session без повторного входа в repository lock; при его отказе откатывается вся транзакция.

`profileUpdate` хранит полные итоговые значения выбранных полей в событии. Strict record validator требует found и сохранения исходного непустого префикса. Только явно одобренные события выбранной линии входят в `storyProfileEntities`: overlays подставляются в видимую карточку и ограниченный игровой/служебный контекст, не переписывая entity rows и другой чат. Перегенерация и подготовка раннего parent исключают поздние overlays; возврат/reload не вызывают новых native jobs. История и предложение сохраняются при снятии подтверждения.

`SceneEntity.profileFieldRevisions` — необязательные локальные версии именно четырёх текстовых полей. Исходный author text + версия должны совпадать с snapshot события; иначе приоритет получает авторская карточка. Сохранение редактора правит в общем каноне только текстовые поля, действительно изменённые пользователем, а не все заимствованные overlays. Явная очистка до прежнего пустого значения тоже создаёт версию, чтобы старое дополнение не воскресало. Портреты/шкалы не создают эти версии. В записи раньше этой функции дополнительного поля нет.

Дальнейший view выбирает baseline по живому bindingId, не по одному адресу чата; архивный checkpoint не захватывает новое прохождение. При неоднозначном read без bindingId view консервативно не выбирает архив наугад. Изменение канона/версии поля подавляет и seed. Backup v4/сейф сохраняют поля; старая строгая сборка может не принять новые необязательные поля, обратная совместимость старого reader не обещается.

Последние 10 предложений выбранного персонажа показываются на экране, все сохранённые записи остаются в истории. Это явный восстановительный инструмент; автоматическое извлечение и одобрение, очереди по всему составу и полный смысловой бюджет остаются RP-04/05 и следующих частей RP-03. Новая автоматизация не включается сама.

Смена head во время подготовки отвергает результат. Уже сохранённое предложение не исчезает, но его нельзя подтвердить после продвижения истории без новой подготовки. Ошибка очистки не уничтожает предложение; успешное сохранение не объявляется отменённой генерацией только из-за отмены ожидания cleanup. ## Действующая большая библиотека Первая часть RP-03

Общие пределы 40 персонажей и 100 накопленных состояний сняты. Нет нового общего числового потолка вместо них. `validCharacterScenes.states`, bonds и сохранённые позиции/циклы портретов проверяют каждую запись, ID, поля и безопасные ключи без отсечения по размеру состава. Пределы worlds/maps, одной физической сцены, сетевого ответа, image plan и объёма импортируемого пакета не превращаются в обещание неограниченных ресурсов.

`selectCharacterContext` рассматривает всю библиотеку текущего чата: герой, собеседники/явный фокус, присутствующие и точные имена/алиасы в реплике и недавнем тексте. Затем набирает реестр примерно на 6000 символов JSON-структуры; уже присутствующие/единственный герой не исчезают из-за необязательных ссылок. Полные анкеты ограничены шестью до RP-05. Unicode NFKC/регистр/пробелы и границы имён обрабатываются локально; склонения/местоимения/семантическая релевантность пока не реализованы. Текущая сцена и реестр отделены от сохранённого состава, ничего не удаляется из библиотеки ради пакета.

Для неоднозначного имени/алиаса игровой prompt использует устойчивые ID вместо одинаковых имён; каталог действий, числовые механики и фото используют тот же режим. `parseStoryUpdate` различает canonical ID и имя нового человека: имя, совпавшее с чужим внутренним ID, не превращает новоприбывшего в того персонажа. Legacy name-receipts не начинают угадывать между совпавшими именами. Полноценное разрешение двойников/маскировки и управляемое слияние — оставшаяся часть RP-03.

Новый человек из выбранного завершённого ответа создаётся через существующий ledger без потолка состава. Физическая сцена по-прежнему до 12; большие словари состояний не отправляются целиком. Повтор/reload не дублируют профиль; отменённый вариант исключает его последствия, возврат восстанавливает прежний ID. Ручное авторское сохранение остаётся отдельным действием, принимающим профиль в общий мир; private playthrough scope не отменён ради общего состава.

`parseCastDraft` сохраняет ограничение транспортного ответа 180000 символов, `parseCastBatch` — размер партии 1/2. `validateCastDraftValue` проверяет весь локально накопленный/редактируемый draft по той же схеме/цитатам, не применяя лимит одного сетевого сообщения к сумме партий. Merge и apply используют его; после 40 нет автоматического character-limit. Исходники операции пока до 220000 символов, `more=false` не доказательство абсолютной полноты; полный native прогон 1000 анкет не проверен. Возобновляемые большие источники и отдельный каталог кандидатов ещё требуются. Эфемерные cast jobs по-прежнему исключены из backup; сохранённые профили/состояния и story ledger входят в него.

Библиотека/галерея отображают до 40 карточек на странице и ищут по всем именам/алиасам. Это UI-пагинация, не ограничение базы или новая необходимость открывать панель при обычной игре. Общий анализ старой переписки и защищённое обогащение существующих постоянных полей не объявляются завершёнными.

## Действующие проверяемые обновления — RP-02 / 206

`parseStoryUpdate` получает завершённый ответ после native-проверки выбранной линии. Сначала проверяются принадлежность world/chat/branch и envelope целиком; неверная область отклоняет всё. Прежний ответ без world/chat допустим только с совпавшей локальной квитанцией точного request/родителя. Один завершённый блок, максимум 64 000 символов JSON / 250 000 ответ. Новые блоки имеют version 2; story records остаются v1 с необязательными строго проверяемыми полями.

Далее независимые поля проверяются отдельно. Поле отсутствует или `{"op":"keep"}` — прежнее значение; `{"op":"set","value":...}` — новое; `{"op":"clear"}` — явная очистка. Пустое legacy-значение означает неизвестное, не очистку. Для состояния разрешены action/condition/goal/relationship/stats; прежние числовые схемы и политики сохраняются. Имена/алиасы сопоставляются однозначно, без нечёткого угадывания. Повтор одного ID отвергается, неизвестные ссылки не образуют частично принятую membership-сцену. Ограничения запроса 12 updates / 12 participants / 24 numeric patches и прежний общий состав 40 остаются до RP-03.

`facts` — максимум восемь предложений `{text,kind,quote}`. `kind`: event/promise/plan/belief. Цитата должна быть точной подстрокой исходной прозы с исходными пробелами/переносами; транспортный JSON и варианты действий не служат доказательством. Предложение — отдельный `StoryEvent.memory` без state/effects, связанный с исходной редакцией. Оно не входит в `acceptedEventIds` до явного `approveStoryFact` пользователя. Редактирование отмечается `edited`; цитата и категория не подменяются. Проверка точной цитаты не доказывает смысловую корректность вывода.

Одобрение/исключение используют текущий world/chat/branch/head/selectionVersion/revisionCount и атомарный пересчёт. Только `projection.appliedEventIds` выбранной линии становятся контекстом. Смена варианта исключает факты отменённого ответа; возвращение восстанавливает их без клона. Проза и исходное предложение не удаляются при снятии одобрения. Это память прохождения, не новые общие MemoryEntry/канон мира. Старые редакции не переанализируются при reload.

`storyFactContext` добавляет до восьми последних подходящих по размеру одобренных фактов с типами, не всеми цитатами: до 600 оценочных токенов данных / четверти настроенного бюджета. Размер инструкции считается отдельно. Служебные/OOC запросы не получают эту игровую вставку. Обещание/план не доказательство исполнения, мнение не объективный факт; относительная дата не превращается в календарную. Релевантный поиск, общий оптимизированный бюджет, периодический анализ и перенос — RP-04–RP-07, не обещание бесконечного серверного контекста.

`StoryRevision.updateDiagnostic` содержит только фиксированные статус, пути/правила, типы/длины и счётчики; `repairDiagnostic` хранит результат отдельной коррекции. `metadataRepair` сохраняет случайный ID/время/состояние requested/done/failed/cancelled. Отчёты без текста/цитат/имён/чат-ID, UI показывает их даже после удаления worker. Журнал ServiceOperation отдельно подтверждает cleanup pending/done/failed; импортированный журнал не даёт права повторить native запрос или удалить чат.

Коррекция — одна попытка на редакцию, минимум 30 секунд между источниками, одна операция в существующем owned-worker lane. `prepareStoryRepair` проверяет текущий выбранный complete assistant без OOC/паузы, фиксирует requested до создания окна и строит запрос по сохранённому ответу/реестру/ошибкам. Флаг автоматизации выключен по умолчанию; активная игра/черновик важнее. `applyStoryRepair` проверяет source/head/frozen character base заново. Разрешено исправить лишь ошибочные state/membership-поля и предложить пропущенные факты. Числа/фото/новые профили не создаются коррекцией. Исходный текст неизменен. Смена линии и даже уход/возврат до результата останавливают старую попытку; уже committed-коррекция выбранного предка может завершить только выдачу/очистку, не примениться повторно. Ошибка политики сама по себе не запускает исправление формата.

Raw prompt/reply живут только в эфемерном owned job, не в открытом session journal. Видимый popup скрывает их непрозрачным служебным экраном; heartbeat поддерживает runtime, не повторяет отправку. Отмена и неизвестная принадлежность чата не разрешают удалять основной чат. При рестарте worker не запускается тайная повторная генерация.

`strictMemorySending` — отдельная выключенная настройка: распознанные обычные fetch/XHR не отправляются при ошибке подготовки/прикрепления. Пользовательский текст восстанавливается только в пустом composer той же страницы/чата; повтор — исключительно вручную. Служебные owned запросы используют свой формат. Это не гарантия распознавания любого будущего endpoint сайта и не доказательство использования фактов моделью. Backup/vault сохраняют источники, предложения, одобрения и correction receipt вместе; старый строгий импортёр может не знать новые optional fields.

## Действующий игровой путь — RP-01 / 205

Пользователь включает отслеживание через «История → Включить запись сцен». Текущие карточки и подтверждённый показанный ответ становятся исходной точкой. Старую переписку расширение не переинтерпретирует и не меняет. В новом подтверждённо пустом чате допустим явный native-root. Повторное включение уже активного прохождения не перезаписывает начало.

`StoryGameClient` читает ограниченный native-снимок обычным GET через исходный авторизованный fetch страницы; нового запроса модели нет. Выбранность определяется показанным native/virtual ID, точно сопоставленным серверному message ID, а не серверным указателем, похожим текстом или номером DOM-строки. Родители берутся только из native-графа. Поддержан подтверждённый текущий контракт `chat/history_messages`; неизвестная схема, пропуск родителя, смена scope или незавершённый ответ останавливают запись. Неизвестные статусы до исходной точки не мешают новой подтверждённой линии после неё.

`runStoryGame` сохраняет исходные тексты, редакции, события, выбранную вершину, проекцию, карточки, новые профили и фото через один repository lock и одну транзакцию. На каждом шаге state-block планируется против пересчитанного точного родителя. Модель не выбирает destination world/chat/base своими строками: они заданы текущей проверенной областью расширения. Без допустимого `<deeprole_characters>` текст сохраняется, но изменения карточек не выдумываются. Семантическое извлечение произвольных фактов из прозы относится к RP-02.

`StoryTurnEffects` связывает с конкретным ответом scene metadata, portrait cycles, идентичности фото и исходные данные созданных профилей/фото. Выбор альтернативы исключает последствия отменённой линии; возврат восстанавливает прежние ID, без дублей и повторного начисления показателей. Новый персонаж, созданный игрой, имеет `playthroughChatId` и не появляется автоматически в независимом чате. Явное ручное сохранение его анкеты переводит её в общий пользовательский канон. Ручные анкеты/лор не переписываются пересчётом.

Фото имеют отдельные результаты генерации. Возврат к готовому фото не запускает API ещё раз; восстановленное незавершённое задание становится expired. Новый платный запуск допустим только для свежего sync, совпавшего с локальной принятой квитанцией, точной закрытой wire-парой и runtime-разрешением той же вкладки. Replay, альтернативы, импорт и backup не создают такого разрешения. Поздний результат отменённой линии не изменяет текущую сцену.

`parent` готовит состояние до родителя запроса; native `edit_message` сначала разрешает точный edited user и его родителя, затем собирает новый контекст. Из старой редактируемой реплики удаляется только ранее зарегистрированный полный injected-prefix для этого native ID; пользовательские похожие маркеры не угадываются. Подтверждённый полный отправленный текст может восстановить исходный draft/OOC для Fetch без wire-ID только при том же точном родителе. Это не доказательство ancestry и не разрешение генерации изображений. Отправка не повторяется расширением.

Ручное расхождение останавливает автоматический переход. «Продолжить, сохранив мои правки» переносит только пользовательскую разницу, не всю отменённую сцену. Изменённый вручную созданный профиль не удаляется молча. Неучтённое удаление/изменение фото требует новой исходной сцены, а не скрытого восстановления. Новая исходная сцена атомарно меняет live binding ID, оставляет старую хронику в хранилище/backup и блокирует устаревшую вкладку. Интерфейса возврата к архивному прохождению пока нет.

«Отменить последнее изменение» возвращает предыдущую пару и приостанавливает автоматическое применение: стрелки/текст DeepSeek сами не изменяются. Пользователь показывает нужный ответ и нажимает «Учесть ответ, выбранный в чате», чтобы возобновить отслеживание. «Вопрос вне игры» отмечает следующую подтверждённую отправку; она и её ответ остаются источниками, но не меняют игровые карточки. Палочки продолжают работать в отдельных служебных чатах.

Сканирование последовательное; смена показанного ответа во время pending GET ставится в повторную очередь. Повтор после reload/из двух вкладок не создаёт событие второй раз. Перед commit и после него проверяется world/chat/URL/vault; старый writer не может одновременно писать managed-сцену. Проверка сейфа под lock не вызывает вложенный repository lock.

Полная копия сохраняет хронику/происхождение и поддерживает шифрование. Экспорт мира остаётся явным переносимым каноном, без текстов хроники и runtime-разрешений. Read/preview — по-прежнему отдельные действия без записи; UI скрывает transport JSON, но исходный ответ хранится целиком.

Границы: native-read ограничен 10 000 сообщениями / 30 MB / таймаутом; пагинация длинной серверной истории относится к RP-07. Общий прежний лимит 40 персонажей снимается в RP-03. Автоматическое извлечение фактов, компактная адресная память, экономия контекстного окна и перенос длинного прохождения в новый чат — RP-02–RP-07, не результат этого включения. Новые optional поля сохранены в прежнем строгом story-контракте; новые backup открываются этой или более новой сборкой, совместимость со старой сборкой не обещается.

Следующие разделы фиксируют состояние до подключения 205. Фразы «не подключено», «нет UI выбора» и прежние защитные ограничения относятся к указанным старым итерациям; актуальное поведение описано выше.

## Единственный владелец сцены

StorySceneOwner сверяет graph и единственную live binding данного chat. В области world/binding/chat допускается максимум одна projection; чужой branch-writer не получает сцену. Проверка выполняется под тем же repository lock, что legacy applyCharacterTurn, planStorySelection или planStoryRequest. Неподтверждённый baseline сам по себе не владеет эффектами и не отключает обычную игру. При существующей projection прежний автоматический writer возвращает character-story-managed до создания entity, изменения состояния/отношений, фото и последующих разрешений генерации. Ручной saveCharacter остаётся разрешённым: ownership не стирается, несовпадение scene требует отдельного разрешения конфликта. Неоднозначная binding не выбирается по порядку массива.

PlanStorySelection не берёт lock, не меняет переданный массив и не пишет; selectStoryRevision сохраняет план через одну общую транзакцию. Вход имеет ровно четыре поля, правильные ID, версию и уникальные явные одобрения; неполный/отсутствующий/чужой источник отвергается. Завершённый user-prefix допустим внутреннему edit/regeneration, но не становится предложением ответа в read-only UI. Optional stillCurrent вызывается после записи под lock; отказ возвращает прежние branch/projection/binding. Exact retry без записи не затирает последующие ручные изменения или фото.

ScenePhotos и lastReply/progress/relationshipNotice/portraitCycles пока не имеют полного revision provenance. Новая baseline содержит необязательный legacyEffects с algorithmVersion 1: точные метаданные scene и идентичности фотографий целевого мира, существовавшие при создании точки. PlanLegacyStory фиксирует их вместе со snapshot/branch под общим lock. Перед первым anchor уже сохранённой точки проверяется этот же список; новый эффект между freeze и anchor даёт story-effects-untracked без записи. Уже anchored точки и повтор ensure никогда не переосмысляют последующие фото как исходные.

Идентичность фото состоит из worldId/entityId/messageKey/turnKey/categoryId/imageKey/createdAt. Порядок массива не важен, количество одинаковых элементов сохраняется. Полный generation, запрос, ticket, illustrationId, статус задания и байты изображения в legacyEffects не копируются. Если исходное queued-фото позже стало ready, внутренний выбор сохраняет актуальный объект фото; не возвращает queued, не отменяет задание, не выдаёт разрешения и не запускает его повторно. Манифест не является ledger генерации или самостоятельной копией image asset.

PlanStorySelection сравнивает текущие идентичности и метаданные с исходными. Совпадающие данные сохраняются без пересчёта. Новое, удалённое или изменённое фото либо несовпадение метаданных дают story-effects-untracked до любых branch/projection/binding writes. Фото другого мира не блокирует переход и не изменяется. Точка без legacyEffects читается, но сохраняет прежнюю консервативную проверку: любые такие эффекты блокируют новый выбор. Автоматического обновления старых точек нет. Snapshot состояний и revision всё ещё защищают ручные правки отдельно.

Кандидаты состояний не заменяют ledger профилей, созданных персонажей, иллюстраций или задания генерации. Read-only preview остаётся математическим расчётом состояний, не проверкой разрешения commit. Нового UI переключения, авторизации или model POST нет. Story v1 и backup v4 получили необязательное поле baseline: эта сборка читает прежние копии, но обратная совместимость новой копии со старой строгой сборкой не обещается. Для такой копии нужно расширение с поддержкой legacyEffects; отказ старого импортера нельзя лечить удалением поля вручную.

## Чтение истории и предпросмотр последствий

ReadStoryReview и previewStoryReview работают только с явным anchored baseline однозначной текущей binding/world/chat. Отсутствие точки даёт пустой read-only результат, не миграцию; неоднозначная привязка и чужой scope отвергаются. Корневая ветка определяется baseline.origin, не серверным current_message_id и не ближайшим текстом. Читается согласованный снимок под repository lock; records/removed всегда пусты. Публичные RPC не вызывают selectStoryRevision, не одобряют кандидатов и не отправляют запрос модели.

StoryReviewPage передаёт не больше восьми редакций, не больше исходного лимита 250000 символов на текст. Offset используется только для списка по createdAt/id; сюжетная связь и parentExcerpt берутся по parentRevisionId. Полные служебные квитанции, injected context и THINK в экран не передаются. Guard содержит branchId, headRevisionId, selectionVersion и revisionCount; новый источник или выбор инвалидирует прежний cursor/preview. Guard — проверка свежести чтения, не подпись, квитанция отправки или разрешение записи. В панели остаётся одна страница, предыдущие не накапливаются.

Preview принимает только завершённый assistant этой ветки либо null для исходной точки. ProjectStoryBranch дополнительно проверяет всю ancestry. Набор acceptedEventIds берётся из уже сохранённой projection, не из входа UI или ответа модели. Результат содержит snapshot и разность appliedEventIds с текущей projection. Current scene сравнивается целиком по states/present/partners и revision; manualConflict сообщает расхождение, но ничего не объединяет и не перезаписывает. Возврат к null отменяет только ранее одобренные последствия в расчёте, не в записи.

Фоновый обработчик требует своего extension sender, главный frame, активную вкладку с точным URL и chat до/после чтения, открытый сейф. Content дополнительно фиксирует текущий world/chat/URL и повторно сверяет их перед возвратом. Панель сверяет active tab/URL перед и после IPC, валидирует форму и проверяет guard/scope/head ответа. При ошибке старые данные и предпросмотр очищаются. Реальный commit не exposed: действующий старый writer персонажей пока не заменён, безопасная передача ему/от него владения сценой остаётся условием включения выбора/отката.

## Наблюдаемая пара после исходной точки

Итерация 201 объединяет prepareDispatchCapture и planStoryRequest в одном updateRecords до CONTEXT_READY. Capture получает необязательный storyBranchId только в той же транзакции, что его StoryRequest с совпадающим ID, миром, binding/chat, purpose и parent. Старые capture без этого поля не получают authority при reload/повторе или после позднего checkpoint. Сохраняются capture contractVersion 1 и backup v4; новый reader принимает прежние capture и проверяет новую ссылку в графе полной копии. Обратная совместимость не обещается: строгий reader старой сборки не знает storyBranchId и может отклонить такую v4-копию. Restored origin запрещает live-приём.

Маршрут создаётся только для local XHR, единственной живой привязки и baseline с явным nativeAnchor. Родитель должен совпасть с выбранным завершённым assistant-head либо исходной точкой при null-head. Проверяются head/version и полный снимок сцены через существующий planner. Изменённая ручная/legacy-сцена, неизвестный родитель, Fetch или отсутствие точки оставляют source-only журнал. Никакой максимальный ID, serverSelection, последний похожий текст или одна найденная альтернатива не выбирают линию. Служебные исходники не получают игровой request.

advanceDispatchCapture атомарно сохраняет HTTP settlement и StoryRequest.delivery. Поддержанные network/aborted/http различаются; redirected/unavailable/superseded остаются в журнале как есть, а story request не получает вымышленный accepted/failed. HTTP-успех не доказывает завершённость, поздний abort потока не переопределяет доставку.

recordDispatchReply захватывает input до await/хеширования; под lock снова сверяет owner/local-origin, live scope, native-связь и полное буквальное равенство wire-text. Общий pure planner существующего exchange-gate записывает user+assistant вместе с dispatch.reply в той же IDB-транзакции. User.content берётся из сохранённого originalDraft, assistant — из проверенных RESPONSE. Сбой записи не оставляет ни половины пары, ни принятого source без редакций; повторное восстановление не отправляет модель ещё раз. Если exchange-gate остановлен, источник может остаться только в журнале, без редакций/последствий.

Наблюдение не двигает head/version, не создаёт projection/events и не изменяет binding/канон. Story-only изменения, как dispatch/service, не объявляются изменением библиотеки: иначе reload мог бы отменить текущую подготовку контекста. Выбор projection включает binding и продолжает оповещать слушателей. Первый пост-checkpoint обмен уже наблюдается production-путём; последующие родители требуют отдельного явного выбора линии. Пока UI выбора нет, они остаются source-only. Старый игровой writer действует прежним способом, новый replay не включён. automaticStoryIngestion: not-connected относится к выбранной хронике и применению событий. Счётчик выбранных ходов и оптимизация памяти остаются RP-04/05.

## Ручная исходная точка

В итерации 200 `readStoryCheckpoint` возвращает актуальный снимок состояния связанного мира и до восьми последних подтверждённых dispatch.reply исходной вкладки. Это ручная read-only операция через content/background repository port. В ответе нет proposedContext, полного wire-text, THINK или чужих сообщений. `availableCount` показывает все подходящие сохранённые источники. Дата — observedAt, не narrative order и не серверный timestamp. Не восстанавливается локальный выбор по serverSelection.

Экран «Настройки → Данные → Исходная точка истории» требует явного выбора native-ответа и подтверждения, что сохранённая сцена относится к нему. Полная реплика/ответ доступны отдельно от помеченной краткой выдержки. Пояснения разделяют ранний серверный ancestor, different и unknown. Пока нет UI выбора корня нового чата/старых страниц источников. Это решение об исходном состоянии, не approval события и не включение автоматической хроники.

`saveStoryCheckpoint` клонирует выбор до await. Под общей library-lock повторно проверяются live binding/world/chat, owner/local-origin источника, подтверждённая injection/delivery, closed+sawFinish+точная пара, sceneRevision и буквальное соответствие полного снимка с историческими именами. Общие pure planners выполняют freeze и anchor в одном updateRecords. При ошибке IDB или изменении активной вкладки/URL до окончания записи откатываются оба story-records; лор/сцена/dispatch не меняются. Посткоммитная проверка области может потребовать повторного чтения, но не повторной отправки модели.

Та же точка повторно возвращает branchId без новых записей. Другая точка/снимок не заменяет существующую. Legacy baseline без nativeAnchor можно привязать только пока его снимок полностью совпадает с подтверждённым текущим и в нём ещё нет requests/revisions/selection; обновление устаревшего исходного состояния не выполняется. Ранее сыгранная история остаётся unknown/unclassified, без разбора задним числом. Сохраняются существующие contractVersion 1 и backup v4, защита сейфа, detach/purge мира. Восстановленная копия — сохранённое состояние, не команда возобновить наблюдение или запрос.

После checkpoint обычная игра пока использует прежний writer. Production-подготовка StoryRequest и наблюдение непосредственно следующей пары подключены в 201; выбор последующего ответа и применение новой projection — следующий обязательный участок. Ни одна запись checkpoint/редакций не включает новый пересчёт скрыто и не создаёт двойное применение последствий.

## Завершённый ответ в журнале отправки

В итерации 199 `dispatch.reply` — необязательное дополнение: прежние записи без него читаются. Оно содержит только окончательный `NativeStorySample`, контракт серверной истории, время наблюдения и `serverSelection`. Сохранённый указатель сервера — не актуальный выбор браузера и не approval. Копии остаются v4; старый build с более узким валидатором не обязан читать новое поле.

После persisted XHR `closed` с `sawFinish: true`, accepted delivery и явным link content регистрирует запрос на чтение пары. Мост выполняет только GET `history_messages`, через неизменённый native fetch; до 30 MB, с ограничением времени. Token остаётся в MAIN world. В поддержанном canonical envelope проверяются session, явные message IDs/parents/roles, user FINISHED без pending fragment и завершение точно указанного assistant. Берётся один буквальный `REQUEST`; ответ объединяет только `RESPONSE` без нормализации символов. `THINK` не передаётся, неизвестные/nontext фрагменты и отсутствие полного текста останавливают чтение. Весь ответ не может превышать 250 000 символов; отказ не заменяется усечённой историей.

Через same-window/same-origin bridge возвращается только эта пара: временный полный user text для сверки и final sample, без других сообщений, reasoning и headers. Background заново проверяет main-frame sender, текущий адрес вкладки, live binding/world, local origin и owner. Под библиотечной блокировкой source должен целиком совпасть с `confirmedDispatchText`; link должен совпасть с сохранённым native association. Только после этого атомарно добавляется reply. Второй экземпляр wire user text не сохраняется. Повтор с тем же ответом не меняет времена/серверный указатель; изменённый ответ не перезаписывает источник. Это контроль целостности наблюдения, не криптографическая аутентификация страницы и не разрешение применять события.

При reload читаются до восьми последних pending captures исходной вкладки, один последовательный проход на загруженную область. Автоматического бесконечного poll/повторной генерации нет. Более старые неподтверждённые строки остаются в журнале; отдельный управляемый repair с пагинацией ещё не реализован. Повтор failed/unknown GET не добавляет ответ. Restored origin не возобновляется. Fetch без наблюдённого native link этим путём не обрабатывается. Обязательная локальная линия всё ещё требует отдельного подтверждения; даже serverSelection `anchor` не разрешает её выбрать.

Новый reader добавляет один GET на поддержанную завершённую отправку. Прежний счётчик контекста также читает этот endpoint, в том числе после reload; объединение этих чтений ещё не выполнено. В тесте число чтений ответа учитывается по его bridge-trigger отдельно от meter. Это экономия повторной генерации, не включённая оптимизация объёма модельного контекста.

`dispatchReplyExchange` преобразует frozen capture в существующий `NativeStoryExchange`: пользовательский sample содержит original draft без добавленной памяти, identities берутся из link, terminal digest вычисляется заново из final sample. Внутренний gate всё равно требует отдельно подготовленный StoryRequest и привязку исходной точки; без них пауза без изменений. Автоматически создавать такой request после ответа, угадывая прошлое состояние, нельзя. Игровой адаптер ещё не включает этот переход. Кандидаты/канон/выбранная сцена не меняются от сохранения source reply.

Точная форма REQUEST/RESPONSE сверена с [публичным web-клиентом DeepSeek](https://fe-static.deepseek.com/chat/static/main.8d6a4f4bfa.js); код изучен как текст, не исполнен. Проверки этого пути перечислены в текущем roadmap. Неизвестная новая версия сервиса остаётся неподдержанной, не повод угадывать схему.

## Постоянный источник обычной отправки

`kind: dispatch`, `format: deeprole-story-dispatch`, `contractVersion: 1` — отдельный журнал, не `StoryRequest`, редакция или событие. При поддержанном обычном POST `/api/v0/chat/completion` с читаемым непустым prompt, явным native-родителем и привязанным миром content до выдачи контекста регистрирует ID запроса и сохраняет исходную реплику, предложенный контекст, chat/world/binding, редакцию сцены и транспорт. Background назначает вкладку-владельца из sender, разрешает только основной frame и сверяет текущий адрес/привязку. Источник копируется до ожидания библиотечной блокировки; неподтверждённая запись не меняет состояние мира.

Мост присылает `STORY_CAPTURE_SOURCE` только после вычисления фактически отправляемого prompt. Принимается целиком равенство оригинальной реплике (`injection: none`) либо точному `context + "\n\n[User message]\n" + draft` (`context`). Разбиение по маркерам, удаление похожего текста и восстановление старых отправок не используются; пользовательские маркеры остаются буквальной частью реплики. Через подтверждение возвращаются только ID и `ok`, не копия лора. Ожидание подтверждения ограничено двумя секундами. Сбой/таймаут не повторяет и не блокирует исходную отправку бесконечно; неподтверждённый журнал не допускает переходы доставки. Смена адреса во время дополнительного ожидания запрещает вставку прежнего контекста.

Зарегистрированный content-клиент проверяет window/origin/точную область, ID, транспорт и родителя и последовательно записывает источник, начало/HTTP-результат и native-сигналы XHR. До 64 одновременно отслеживаемых запросов — защитный предел очереди, не длительности истории. Навигация, закрытие сейфа и смена мира исключают поздние сообщения; другая вкладка не может дописать журнал владельца. Исходник/маршрут/пара неизменяемы; одинаковая доставка не создаёт повтор и не меняет время. HTTP-принятие отдельно от отказа/ошибки/отмены потока. `ready`, `finish`, `closed`, `failed` описывают wire, не разрешают применение событий. Fetch-ответ не читается и сохраняет `wire: waiting`; это не ошибка и не подтверждение завершения.

Журнал не публикуется как правка библиотеки и не запускает обработку анкет. Тексты защищаются сейфом наравне с исходными редакциями; закрытый сейф не допускает чтение/запись. Полная копия с dispatch получает envelope v4, прежние v1–v3 продолжают читаться. Восстановление устанавливает `origin: restored`: историческая запись не возобновляет сетевую операцию. Несовпадающая запись того же ID при merge отклоняется. Экспорт одного мира исключает журнал. Удаление только организации отсоединяет worldId; явное удаление всего лора удаляет связанные строки.

Предел одной записи: исходная реплика до 100 000 символов, предложенная память до 500 000; превышение не меняет запрос сайта, лишь запрещает его регистрацию. Сохранённый журнал не имеет общего лимита строк. Индексация/чтение больших журналов — RP-07: текущие транзакции читают нужные типы записей, не являются измеренной масштабной реализацией. Обработка retry/regenerate/edit/continue и Fetch native-пары, возобновление после reload, обновление служебной диагностики и применение через выбранную хронику остаются отдельными задачами. Палочки и старые квитанции не переводятся в этот журнал по эвристике.

Проверки: `tests/story-dispatch-capture.test.ts`, `tests/story-dispatch-capture-client.test.ts`, дополненный transport test и `tests/e2e/story-dispatch-capture-runtime.spec.ts`. Последний выполняет настоящую цепочку установленного MV3 content → background → extension IndexedDB на синтетическом API и проверяет RU/EN, Fetch/XHR, точный prompt, перезагрузку и неизменность лора. Это не проверка личного DeepSeek и не доказательство принятой истории.

## Видимая презентация служебных запросов

Итерация 193 распространяет focused popup и непрозрачную маску на подготовку состава. Тексты этого режима не используют имена/поля, а описывают отправку фрагментов лора и последовательную подготовку анкет. `deeprole_cast_screen` хранит только UUID/язык и отделён от `deeprole_field_screen`; ни один маркер не разрешает отправку, принятие ответа или удаление. Worker состава получает права только через прежний background claim. Проверка полного ответа, частичных checkpoint, исправления и удаления своего чата не ослабляется. Явное открытие остановленного/завершённого чата может снять маску, но не отправляет запрос повторно.

Окно worker создаётся с `focused:true`. До асинхронной инъекции/claim на `document_start` локальный opaque screen закрывает native-интерфейс. Имена/названия полей передаются только подтверждённому worker в `Job.presentation` и не входят в Owner, служебный журнал или outbox. Человекочитаемая плашка не заменяет настоящий протокол запроса и не ослабляет проверку ответа.

Сессионный маркер страницы содержит только UUID запроса и язык; он нужен для сокрытия при reload и не даёт права отправки, принятия ответа или удаления. Любая работа требует прежнего claim владельца из background. Без подтверждения показывается остановка, не отправляется запрос и не удаляется чат. Native DOM сохраняет layout/visibility для существующего adapter и ownership-checked удаления; экранный диктор получает только локальную плашку. При явном ручном раскрытии маска и её атрибуты снимаются без удаления native-узлов.

Отмена из плашки относится к собственному запросу: фиксируется `cancelled`, повторной отправки нет; затем проверяется очистка. Принятый текст остаётся черновиком. Срок ожидания очистки, позднее подтверждение и блокировка очереди при незавершённой очистке сохранены. UI показывает только наблюдаемые события, без выдуманного процента/ETA; наличие блока размышлений не раскрывает его текст и не доказывает чтение всей истории.

Worker больше не заменяет последний рабочий `runtime.stage` общим `cleanup`/`finished`. Статус операции и очистки остаётся в существующих `phase`/`cleanup`; старые фиксированные значения V4 читаются. Это улучшает диагностику ожидания, но не подтверждает native completion для RP-01. Работа по-прежнему зависит от видимого окна; отдельный native-транспорт невидимого получения/удаления не реализован. Сокрытие локальное: DeepSeek получает настоящий запрос; при DevTools/ручном раскрытии он доступен.

## Реализованная основа RP 01

Записи `kind: story` находятся в существующей таблице `records`: отдельная таблица и повышение версии IndexedDB не понадобились. Каждая запись содержит `format: deeprole-story`, `contractVersion: 1`, локальный ID, область мира/прохождения/ветки и время создания. Есть шесть типов: `baseline`, `branch`, `revision`, `event`, `projection`, `request`.

- `ensureLegacyStory` по явному внутреннему вызову сохраняет исходное состояние одной пары чата и мира: состояния участников, присутствующих, партнёров и исторические имена. Анкеты, изображения и существующие записи не переписываются. Прежняя история помечена неизвестной; старые журналы показателей не превращаются в новые события. Повторный вызов сохраняет прежнюю исходную точку, даже если текущая сцена уже вручную изменена.
- `recordStoryObservation` одной транзакцией записывает исходный текст редакции и связанные кандидаты. Хранит внешний ключ сообщения, локальные ID сообщения/редакции/запроса, родителя, роль и завершённость. Передающий код обязан заранее назначить стабильные локальные ID и повторно использовать их при повторной доставке. Тот же ID с другим содержимым отклоняется. Проверяются область родителя, участники и точная цитата; наличие цитаты не доказывает правильность вывода модели.
- Кандидат имеет `disposition: candidate`, порядок, участников и предполагаемые состояния до/после. Его сохранение не выбирает редакцию, не меняет текущую сцену, не начисляет показатели и не добавляет факт в канон. Предложения из частичного или прерванного текста также остаются только кандидатами.
- `readStoryTimeline` читает исходную точку, наблюдения, квитанции и сохранённую проекцию ветки. В хранилище нет общего потолка персонажей или обрезания хроники до 20 записей. Ограничения старого игрового пути ещё существуют до RP-03. Чтение и проверка пока загружают все записи нужных типов; постоянные индексы и нагрузочные измерения относятся к RP-07.

Граф проверяется отдельно от формы каждой записи: исходная точка принадлежит корневой ветке; ссылки не пересекают миры и прохождения; родители существуют; циклы, повторные исходные точки и одинаковые позиции события в одной редакции отклоняются. Чтение повреждённого графа останавливается, а не молча исправляет его. Пока нет публичного запроса из контент-скрипта на запись этих данных и нет автоматического запуска при старте расширения.

Резервная копия без хроники и журналов остаётся версии 1. При наличии только `story` создаётся версия 2; при наличии `service` — версия 3; при наличии `dispatch` — версия 4. Поддерживаются все четыре версии; старые версии расширения не смогут прочитать новую копию. При восстановлении проверяется весь граф, а слияние одинаковых ID с разным содержимым или независимо созданных исходных точек одной пары чата/мира отклоняется до записи. В таком конфликте нельзя автоматически выбирать одну историю; объединение вариантов остаётся будущей отдельной операцией.

Сейф шифрует все шесть типов, в том числе новые наблюдения, квитанции и проекции после включения шифрования; закрытый сейф блокирует чтение и запись. Полная резервная копия включает исходные тексты наблюдений и исторические имена: для защиты переносимого файла следует выбирать копию с паролем. Пакет экспорта одного мира не включает хронику прохождения. Удаление только организации мира сохраняет историю с `worldId: null`; полное удаление лора удаляет связанные записи хроники. Удаление текущей анкеты не переписывает исторические имена и участников; эти ссылки не означают восстановление удалённой анкеты.

Настоящий путь хранения проверяют `tests/story-storage.test.ts` и `tests/story-backup.test.ts`: повтор/конкурентная доставка, повтор после reopen, атомарный откат после частичной записи, защита содержимого, изоляция чатов, больше 20 событий, резервные копии, закрытый сейф, организационное и полное удаление. Это проверки Dexie/fake-indexeddb и WebCrypto, не прогоны личного аккаунта DeepSeek.

## Учёт служебных операций

`service` — отдельный журнал работы палочек текстовых полей, плана иллюстрации и подготовки состава персонажей, не редакция сюжета и не `NativeStoryPurposeReceipt`. Назначение задаёт background-координатор до создания временной вкладки; публичного write RPC для этого типа нет. Сохраняются локальный ID операции, мир, исходный и временный chat ID, режим `history`/`suggest`, категория, этап, результат очистки и разрешённый код ошибки. Запрос, ответ, имена, произвольные названия полей, цитаты, изображения, адреса и ключи не включаются.

Итерация 186 добавила `operation: cast-preparation`, `fieldScope: cast`, `mode: history`, `sourceChatId: null`: подготовка читает библиотеку мира, а не привязывается к конкретному игровому чату. Промежуточные батчи и попытка исправления формата остаются этапом `dispatching`. Только готовый полный состав получает `result`; частичный ответ, отказ или отмена — `failed` с фиксированным кодом. Готовые части и подробная диагностика по-прежнему хранятся в прежнем `CastJob`; служебная отметка не содержит анкет. Ручное сохранение части после ошибки не превращает всю подготовку в успешную.

`prepared` означает регистрацию до создания worker; `dispatching` — локальный запрет повторной отправки, записанный **до** нажатия кнопки; это ещё не сетевой успех. `result` означает принятие предложения существующим валидатором палочки, не подтверждение native-завершения и не сохранение анкеты. `failed` и очистка `pending`/`done`/`failed` учитываются отдельно: правильное предложение возможно при неудачном удалении временного чата. Перезапуск background не возобновляет отправку и не восстанавливает текст ответа.

Запись сохраняется после удаления временного чата и подтверждения получения предложения. Повторные неизменённые опросы не читают журнал заново и не меняют дату; этапы не откатываются, привязанный временный чат не подменяется. После полного удаления мира поздний worker не воссоздаёт ни мир, ни запись. Удаление только организации отсоединяет запись с `worldId: null`. Служебный прогресс не публикуется как правка лора и не перезагружает редактор/очередь.

Журнал защищается сейфом и входит только в полную резервную копию. После восстановления `origin: restored` остаётся историческим происхождением: даже файл с `origin: local` не получает права продолжить локальную операцию. Слияние несовпадающих записей одного ID останавливается до записи; совпадающая локальная запись не заменяется импортированной. Переносимый пакет мира не содержит журнал и не принимает его при импорте.

Если сейф закрыт или запись временно недоступна, очистка принадлежащего worker остаётся разрешённой. Итерация 185 добавила постоянную очередь `deeprole_service_pending:`: перед подтверждением получения предложения записывается случайный UUID операции/токена, фиксированные этап/очистка/код и время. В этой незашифрованной очереди нет world/chat ID, адресов, запросов, ответов, имён или ключей. Привязка временного чата берётся только из защищённого журнала либо текущего владельца session и вне сейфа в очередь не копируется.

Очередь проверяется при запуске background, разблокировке, изменении библиотеки, следующем запуске палочки и создании полной копии. После восстановления доступа её метаданные дописываются в существующий локальный журнал без отправки модели, восстановления текста или сохранения анкеты. Потеря session не мешает доставке, если привязка уже записана в журнале. При сбое удаления уже доставленной отметки повтор очищает остаток, не применяя его заново. Записи удалённых и импортированных операций отбрасываются; очередь не переносится в backup как исполняемое задание.

Ограничения: очередь вмещает 128 отложенных операций, не персонажей; старые записи не вытесняются. При недоступности очереди достаточна успешная запись самого журнала; у палочек полей при недоступности обоих хранилищ отправка/подтверждение получения не разрешаются. Если результат потерял привязку и в журнале, и в session, он остаётся отложенным — чат не угадывается. Повреждённые записи не исполняются и автоматически не исправляются. Очистка профиля браузера удаляет и очередь, и базу; восстановление текста ответа после этого не обещается. До доставки журнал показывает последний записанный этап, а не обязательно текущий итог.

У подготовки состава есть дополнительная опора: сохранённый локальный `CastJob`. При запуске, разблокировке, следующей операции и проверке статуса из него можно дописать уже существующую локальную служебную запись после сбоя обоих audit-хранилищ. Старые задания без регистрации и восстановленные отметки не получают новую регистрацию задним числом. Потеря владельца активного задания не открывает новый worker: задание отмечается прерванным, а новый запуск требует явного повтора и решения вопроса очистки. Это не восстановление потерянных анкет после удаления профиля.

Итерация 187 разрешает cast-worker очистку при закрытом сейфе. Перед остановкой генерации, открытием удаления и подтверждением worker получает разрешение background на точный принадлежащий ему chat ID и повторяет проверку текущего адреса. Вложенный frame, другой чат, потерянный владелец или непривязанный чат не получают разрешение. Отмена и автоматическая навигация проверяются также после паузы перед отправкой. Пользовательский ввод по-прежнему запрещает удаление затронутого чата.

В session сохраняются фиксированные служебные этапы и ранее известная привязка, без анкет, запросов, ответов и произвольного текста. Блокировка разрешает только чтение признака очистки и её итог; задания модели, ответы и checkpoint не читаются/не записываются. Активная подготовка получает `vault-locked`; уже готовый/частичный исход не заменяется новым успехом. Итог пишется в постоянную очередь без chat/world ID. Если очередь и журнал недоступны, marker остаётся в session, но успешное подтверждение/закрытие worker не выдаётся. Потеря session одновременно с недоступностью этих хранилищ не покрывается.

После разблокировки журнал и существующий локальный `CastJob` сверяются одной транзакцией по ID, миру, дате создания и точной привязке. Готовые анкеты, проверенные checkpoint и ручные изменения сохраняются; незавершённое задание останавливается без нового запроса. Запись cleanup идемпотентна; если запись задания не удалась после удаления отметки из очереди, следующий запуск использует уже сохранённый журнал. Привязку можно восстановить только из защищённого задания с той же локальной регистрацией, не из похожего текста или импортированной отметки. Удалённые задания не воссоздаются; применённые анкеты/лор не изменяются. Отсутствие вкладки означает неизвестную/неудачную очистку, а не удаление native-чата. Перед закрытием очищенного worker его текущая вкладка проверяется ещё раз.

Ни `origin: local`, ни этап `result`, ни один chat ID не связывают операцию с точным native-ответом: для будущей хроники нужны отдельные проверенные parent/link/HTTP/lifecycle сведения. Сам журнал не подключён к автоматическому приёму сюжета. Прочие служебные инструменты пока не регистрируются этим типом.

### Видимость и ограниченное ожидание очистки палочек 191

Отдельные палочки используют `windows.create({ type: popup, focused: false, width: 520, height: 720 })` с единственной активной страницей и таким же incognito-режимом, как у источника. Созданная `about:blank` принадлежит операции до перехода на DeepSeek; не используется скрытая вкладка в игровом окне и не запрашивается фокус исходного окна. Сбой создания не приводит к запасной отправке в основной чат. Отрисовка настоящего сайта всё ещё зависит от видимости страницы: минимизация не поддержана как надёжный фоновый путь.

Контракт операции V4 разрешён только для `character-field`. Обязательные поля `validation` (прежняя безопасная диагностика или `null`) и `runtime: { stage, visibility, at }`. `stage` принадлежит закрытому списку `opening/ready/sending/waiting-reply/reply-received/cleanup/finished`, `visibility` — `visible/hidden/unknown`; время ограничено диапазоном безопасной даты. Произвольные поля/строки отклоняются. Этап не откатывается, повтор одинакового этапа/видимости не переписывает запись. Прогресс видимости не меняет `phase`, смысл `updatedAt` или лор, не публикует библиотечную правку, не является квитанцией отправки/завершения. Запись идёт только по точной локальной регистрации; импортированный либо удалённый журнал не дописывается и не возрождается.

Отчёт служебных операций v4 проецирует только три разрешённых поля `runtime` или `null`; V1/V2/V3 продолжают читаться без выдуманных шагов. Не зашифрованный outbox служебного прогресса не расширен: сырые ответы, источники и новые подробности в него не помещаются. Полная резервная копия по-прежнему v3 и сохраняет V4 только внутри защищённого журнала; восстановленная операция остаётся исторической.

После принятия результата или ошибки координатор отмечает `settledAt`. Когда подтверждения очистки нет 20 секунд, source получает готовый черновик либо ошибку с предупреждением `cleanup: failed` и ссылкой на принадлежащий операции чат. Это означает **удаление не подтверждено**, а не доказательство неудачной попытки: сохранённая запись остаётся `cleanup: pending` до реального сообщения worker. Время отсчитывается от принятия результата/ошибки, не является новым лимитом генерации. ACK принятого результата может освободить эфемерный текст и отметить `delivered`; владелец сохраняется до поздней очистки. Такой ACK не превращает последующую очистку в прерывание из-за отсутствия текста. Пока очистка не завершена, новый worker не создаётся. Перезапуск не восстанавливает ответ и не повторяет запрос.

`fieldHistoryAnchor(root, true)` разрешает точный `data-virtual-list-item-key` только для ручного reply probe. Последний пригодный видимый ключ должен быть допустим, уникален, не принадлежать размышлениям/скрытому служебному сообщению и не противоречить явному `data-message-id`. Сервер проверяет строгое совпадение: `matched` либо `not-in-history`; позиция, похожий текст, числовой разбор и угадывание префикса не используются. Обычное извлечение фактов вызывает функцию без этого флага: отсутствие прямого message ID всё ещё не разрешает виртуальный ключ как доказательство ранней истории. Native-диагностика остаётся v3, автоматическая хроника не включена.

Проверки 191: 140 файлов / 2396 тестов (8 прежних todo), TypeScript, 162 общих браузерных сценария; ещё 32 сценария диагностики повторены после добавления интерфейса runtime. Совместимость V1/V2/V3/V4, строгие закрытые значения, vault/backup/purge, временное отсутствие записи, иностранный worker и поздняя очистка проверены на синтетических данных. Активная служебная страница проверена без ручного открытия на render-gate fixture; настоящий native popup и установленная копия DeepSeek остаются отдельным живым критерием. Сборки/ZIP Chrome и Firefox MV3 свёрены по SHA-256, 24/24/404 файла. Автоматическая хроника не включалась.

### Точные безопасные причины отдельных палочек 190

`ServiceOperation` V3 разрешён только для `character-field` и добавляет `validation: { family: field, events, excluded }`. V1 без подробностей и V2 подготовки состава продолжают читаться; новые операции без отклонённого ответа остаются V1. Служебный отчёт строится как v3, читает старые v1/v2 и проверяет соответствие семейства операции. Это не версия native-диагностики истории. Полная резервная копия остаётся версии 3; её восстановление не возобновляет операции. Переносимый мир по-прежнему не содержит журнал, purge удаляет его.

Причины создаёт настоящий локальный валидатор JSON/цитат, обычного текста или плана иллюстрации. Прежние правила принятия, коды ошибки и ограничения сохранены: проверка схемы/дословности не подтверждает истинность вывода модели. Сообщения `not-found`/`conflict` означают результат поиска DeepSeek, а не установленное отсутствие факта или доказанное противоречие. Изображение здесь — только текстовый план; ошибки внешнего провайдера этим контрактом не покрываются.

Background принимает подробности только после проверки своего worker, регистрации отправки, временного чата и задания. Отдельная атомарная запись требует существующую локальную регистрацию с совпадающими миром, исходным чатом, временем, режимом, категорией поля и известным worker. Worker не может совпадать с игровым чатом. Импортированная, удалённая или чужая запись не дополняется; поздний ответ не восстанавливает удалённый мир. В контракте одна попытка, без автоматического исправления или повторной отправки; первая записанная причина не заменяется повторным снимком.

Сохраняются до 60 причин: стандартные пути с числовыми индексами, закрытые правила (длина текста — ограниченное целое), только тип/длина/число полей полученного значения, время и длина ответа. Нет пользовательских названий полей, источников, цитат, содержимого ответа или произвольных сообщений исключений. Небезопасные подробности исключаются со счётчиком. Правила и пути протокола раскрываются отдельно от RU/EN пояснений. Копирование и чтение повторно проверяют контракт, не запускают модель, reconcile, запись или очистку.

Запись подробностей не меняет phase/cleanup/error/updatedAt и не публикует правку лора. Сохранённая причина переживает удаление временного чата/задания и перезапуск. Если защищённая запись не удалась, безопасные подробности повторно записываются только пока жив этот background; они не помещаются в незашифрованный outbox. Если одновременно запись не удалась и background перезапустился, причина может потеряться: остаётся прежний общий код, подробности не придумываются. Основной учёт и очистка при этом продолжаются независимо.

Проверки 190: 140 файлов / 2386 тестов, 8 прежних todo, typecheck; 158 общих сценариев Chromium/Firefox, включая настоящий parser/coordinator, несовпадающую цитату, нехватку источников, слишком длинный текст, неверный план, иностранный worker, повтор, сбой записи, перезапуск, vault/backup/purge, V1/V2/V3, RU/EN и панели 320/760 px. Сопоставление с прежним валидатором выполняется на синтетических вариантах, не на личном лоре. Живая установленная копия не проверялась.

### Точные безопасные причины подготовки 189

На этапе 189 `ServiceOperation` V1 сохранялся без дополнительных полей. V2 разрешён только для `cast-preparation` и добавляет `validation: { family: cast, events, excluded }`. Отдельные палочки получили подробности в V3 на этапе 190 выше. Полная резервная копия остаётся версии 3; старая версия расширения может не читать новые контракты журнала. Восстановленные записи остаются историческими и не получают права дописать диагностику; переносимый пакет мира не содержит служебный журнал, полный purge удаляет его вместе с миром.

Background атомарно читает существующие защищённые `CastJob` и локальную зарегистрированную служебную запись; должны совпасть ID, мир, дата создания и уже известная привязка временного чата. Он проецирует только события этого request ID с этапом `parse`/`merge`. Не читает текстовые `issues`, источники, цитаты, причины персонажей или размышления. Протокол пути допускает только стандартные поля/числовые индексы; правила — точный закрытый список; `actual` — тип/длина или несколько фиксированных признаков неполного JSON. Произвольное значение заменяется на `null`, неизвестное правило/путь исключается со счётчиком. Событие содержит step/repair, разрешённый код, этап, время и длину ответа, без его содержимого.

Журнал сохраняет до 24 новых безопасных попыток по 60 причин. Новые причины объединяются с уже сохранёнными, поэтому старый снимок или вытеснение строк worker из диагностического окна задания не стирают прежнюю попытку. Повтор не пишет новую запись. Диагностика не изменяет coarse phase/cleanup/error/updatedAt, не объявляет правку лора и не влияет на отправку или исход проверки. Её сбой не блокирует основной audit; reconcile может повторно прочитать оставшееся локальное задание, не отправляя модель. Если запись причин не успела сохраниться и задание утрачено, их восстановление не гарантируется. Незашифрованный outbox остаётся прежним ограниченным контрактом, без этих подробностей.

Служебный отчёт теперь строится как v2 и включает только эту безопасную проекцию; прежний отчёт v1 также читается. Экран/копирование повторно проверяют точные ключи/правила и пересобирают данные. Ручная кнопка всё так же не читает `CastJob`, не запускает reconcile/flush и ничего не записывает. Успех после исправления не стирает историю отклонённых попыток и не становится из-за неё текущей ошибкой. Отсутствие подробностей означает «не сохранены», не предположение о цитатах или отказе модели. Это не доказательство native completion, выбранной редакции или ручного сохранения анкеты.

### Безопасный служебный отчёт 188

Ручная сводка в настройках читает только `service` и отдельные отметки outbox. Не читает `CastJob`, лор, переписку или session-владельцев; не вызывает flush/reconcile, записи базы, RPC модели, открытие/удаление вкладок или очистку чата. Перед чтением защищённого журнала и после него проверяется сейф. Закрытый сейф и сбой источника дают неизвестный счётчик (`null`), а не пустой источник. Отчёт — снимок, не атомарная совместная транзакция двух хранилищ.

Проекция разрешает только категории, режим/область, этап, очистку, фиксированный код ошибки, время, исторический origin и случайный `cast_/field_` UUID. World/chat ID, URL, названия, произвольные ID и токен очереди не передаются. Старый ID заменяется на `null`; повреждённая запись и неизвестные дополнительные поля исключаются со счётчиком, не с пересказом содержимого. Перед отображением/копированием проекция повторно проверяется и собирается заново. JSON содержит `readOnly: true`, `nativeCompletion: not-verified`; это не native-квитанция и не факт ручного сохранения анкеты.

Журнал и очередь не сливаются в якобы подтверждённое текущее состояние. Очередь может содержать уже записанную отметку после сбоя удаления; её наличие не доказывает потерю результата. Импортированный журнал обозначен как история, не разрешает исполнение. До 50 новых строк каждого источника входят в экран/JSON, счётчики охватывают все допустимые строки. Это размер отчёта, не лимит памяти или персонажей. Поле отчёта на экране не сохраняется отдельно в незащищённое хранилище; долговечность обеспечивает прежний журнал/очередь. Пропавшие старые задания не восстанавливаются. На этапе 188 точные ошибки схемы/цитат не переносились; безопасная проекция добавлена в 189 выше.

## Пересчёт и выбор состояния RP 01

`projectStoryBranch` — чистый пересчёт проверенного графа. Он начинает с неизменённой исходной точки, идёт по родительской цепочке выбранной редакции и применяет только явно принятые события в порядке редакций и их `ordinal`. Другие альтернативы и их потомки остаются в архиве, но не участвуют в результате. Возврат к прежнему варианту заново получает его состояние, а не ещё раз прибавляет числовые изменения. Для корневой ветки выбор `null` возвращает исходное состояние.

Принятие хранится отдельно от неизменяемого кандидата: `projection.acceptedEventIds` содержит локально принятые события, в том числе временно невыбранных вариантов, а `appliedEventIds` — события текущей цепочки. Список принятия нельзя получать непосредственно из ответа модели. Он пока задаётся явным внутренним вызовом; экран проверки и политика автоматического принятия ещё не реализованы.

Перед каждым принятым событием проверяется совпадение состояния `before`. Отсутствие обязательного предыдущего события, несовместимые состояния участников или несовпадающее членство сцены останавливают пересчёт целиком. Неизвестный родитель, цикл и два варианта одного сообщения в одной цепочке не исправляются догадкой. Незавершённые и прерванные источники нельзя применять: их кандидаты остаются доступными в архиве. Переход участников и партнёров задаётся отдельным проверяемым `sceneChange`; отсутствие перехода оставляет прежний состав сцены.

`selectStoryRevision` под общей блокировкой библиотеки одной транзакцией сохраняет выбранную вершину, версионированную проекцию и состояние текущей сцены. Вызывающий код передаёт ожидаемую вершину и `selectionVersion`. Конкурирующий выбор из другой вкладки отклоняется. Непосредственный повтор завершённой операции распознаётся по предыдущей вершине, версии и тому же списку принятия; он ничего не записывает. Старый повтор после переключения туда и обратно не считается новой командой.

Текущее состояние и редакция сцены должны совпадать с последним результатом пересчёта, либо с исходной точкой при первом выборе. Ручная правка состояния, даже с последующим возвратом текста, останавливает новую операцию с конфликтом. Независимые правки анкеты, лора и остальных привязок сохраняются. Повтор уже выполненной операции не стирает более позднюю ручную правку. Ручной конфликт пока только безопасно выявляется; отдельный способ разрешения и сохранения ручного изменения в хронике ещё впереди.

Применение сейчас ограничено корневой веткой и её исходным чатом/миром. Чистый пересчёт умеет учитывать явно заданный префикс дочерней ветки, но запись такой ветки требует отдельной маршрутизации и пока отклоняется. История удалённого мира читается как архив, не становится активной сценой. Удалённая анкета не восстанавливается состоянием без профиля. Старые ограничения валидатора текущей сцены ещё действуют: превышение останавливает запись, а не сохраняет повреждённую привязку.

Проекция имеет `algorithmVersion: 1`. При чтении и восстановлении её цепочка, список применённых событий и снимок заново проверяются пересчётом; один маркер версии не считается доказательством целостности. Проекция и сцена шифруются вместе с остальными записями. Технический конфликт содержит код, путь поля и локальные ID, но не исходные тексты и значения состояния.

`tests/story-projection.test.ts` и `tests/story-selection.test.ts` проверяют три альтернативы, замену раннего ответа и пользовательской реплики, возврат к исходной точке, числовые состояния без повторного начисления, независимые ручные изменения, две конкурирующие операции, непосредственный и устаревший повтор, частичный сбой транзакции, reopen, сейф, резервную копию, подменённый кэш и удаление. Фикстура на 1200 событий проверяет итеративный обход без рекурсивного стека, а не устанавливает предел истории или заявляет нагрузочную готовность.

Эти API ещё не вызываются игровым адаптером. Автоматическая связь с выбранной редакцией DeepSeek, наблюдение, отмена зависимой памяти/изображений и интерфейс истории остаются частями RP-01 и последующих этапов. Пересчёт состояния сам по себе не устраняет старую ошибку приёма перегенерированного ответа на сайте.

## Квитанции доставки и происхождение редакций RP 01

`readStoryTransportIdentity` различает явно переданный `parent_message_id: null` и отсутствующий/нечитаемый родитель. Число 0 сохраняется как ID сообщения, а не объявляется началом чата. Квитанция не восстанавливается по URL, похожему тексту, позиции виртуального списка или числу сообщений. Неизвестные формы запроса не получают подтверждённую родословную.

Сетевой перехватчик передаёт в запрос контекста только ID чата и канонический ключ родителя; успешная доставка содержит HTTP-статус. При наличии этих полей они сохраняются в существующих метаданных вкладки. Поток ответа не читается и не заменяется, повторная отправка не производится, токены сайта и полный сетевой ответ в квитанцию не попадают. Эти метаданные ещё не создают `request` в хронике автоматически.

### Сигналы обычной отправки

Итерация 176 добавляет отдельный временный пакет `NATIVE_STORY_DISPATCH` для распознанного same-origin POST через Fetch/XHR. Он содержит только локальный `requestId`, транспорт, фазу, ID чата и точный ключ родителя; итог — HTTP-статус или разрешённый код ошибки. Нет текстов, адресов, имён, заголовков, токенов и model request ID. ID назначается при подготовке и совпадает с ID запроса контекста, когда такой запрос был нужен. Native-метаданные копируются до ожидания памяти: две параллельные отправки не используют последнюю общую привязку вкладки.

- `started` публикуется непосредственно перед вызовом исходного транспорта; `settled` — не более одного раза. Это вызов транспорта, не доказательство фактического получения сервером или принятого игрового хода.
- `accepted` означает только наблюдавшийся HTTP 2xx. Ошибки HTTP/сети, отмена до заголовков, недоступный статус и замена незавершённого XHR различаются. Fetch с `redirected` не принимается как доставка исходному endpoint; XHR не предоставляет эквивалентного флага, его HTTP-статус сам по себе также не доказывает назначение ответа.
- Отмена/ошибка после заголовков не переписывает квитанцию доставки и **не** означает завершение модели. Поток не читается, `loadend`, 200 и EOF не используются как доказательство завершённой редакции.
- Пакет появляется и при пустом/неполученном контексте, и при известной структуре native-запроса без `prompt`. Во втором случае назначение запроса не угадывается: это может быть повтор ответа, а не новый пользовательский ход.
- Служебные запросы, неизвестный родитель, неподдерживаемые тело/маршрут и не-POST не получают эти пакеты. Неизвестный родитель не заменяется корнем; `null`, `0` и строковый `"null"` различаются. Синхронный XHR не ждёт хранилище и отправляет исходное тело.
- Нет автоматического повтора, изменения DeepThink, долговременного журнала, новых таймеров или чтения пользовательской истории. Отказ `postMessage` не останавливает отправку; отмена и повторное открытие XHR снимают его старые слушатели, Fetch снимает новый слушатель отмены после заголовков/ошибки.

`validStoryDispatchPacket` отвергает лишние/неизвестные поля, неверные ID/ключи и неподходящие HTTP-статусы. Это валидация структуры, **не** защита от подделки другим JavaScript страницы: page-сигнал сам по себе не является доверенной квитанцией и не может разрешать запись истории. Content/background пока не потребляют новый тип для записи `request`, выбора линии или приёма пары. Следующий драйвер должен сопоставить его с заранее сохранённой квитанцией, действительным native-ответом и подтверждённым состоянием его точной редакции. Проверки на локальном mock не подтверждают актуальный live-формат DeepSeek.

### Внутренняя сохранённая квитанция

`prepareStoryRequest` сохраняет локально назначенный ID запроса, мир/прохождение/ветку, привязку чата, точную родительскую редакцию, выбранную вершину и версию, редакцию сцены и назначение запроса. Новый ход следует за выбранным завершённым ответом; повтор ответа следует за выбранной пользовательской репликой. Первый ход без локальной родительской редакции допустим при пустой выбранной цепочке: после явного корня либо после отдельно привязанной исходной точки старого чата. После явной привязки разрешена и новая редакция первой реплики после этой точки, даже при непустой выбранной цепочке; неизвестное начало старого чата не объявляется корнем задним числом. Интерфейс привязки ещё не реализован. Неизбранная альтернатива, неправильная роль родителя, смена ветки или ручного состояния останавливают подготовку. Переходы дочерних веток пока не маршрутизируются.

Выбранная вершина и редакция сцены в квитанции защищают от конкурентной правки, но не задают содержимое будущего запроса. Внутренний контекст теперь пересчитывается до её точного родителя и фиксирует использованные разрешения событий. Подключение к обычной отправке на сайте ещё впереди; одной квитанции недостаточно, чтобы объявить готовой перегенерацию на сайте.

Подготовка, HTTP-приём и ошибка — разные состояния. `settleStoryRequest` атомарно завершает подготовленную квитанцию один раз; конкурентный противоположный результат отклоняется. Непосредственный повтор с тем же результатом ничего не записывает. HTTP 2xx подтверждает лишь принятие сетевого запроса: завершённость, успешность ответа приложения и пригодность событий проверяются отдельно. Поздний abort не переписывает уже принятую квитанцию. Ошибки хранят ограниченный код `network`/`aborted`/`http` и статус, не текст исключения или ответа.

`recordRequestedStoryObservation` требует явного `requestProof`, принятой локальной квитанции и точного внешнего родителя. Для обычного хода сохраняется пользовательская редакция с родителем квитанции, а ответ ссылается именно на неё. При повторе ответа источником становится другая редакция ответа на выбранную пользовательскую реплику, а не потомок отменённого ответа. Один запрос не привязывается к постороннему пользовательскому или ответному сообщению. Только совпадение `requestId` в модельном JSON не превращает старое наблюдение в подтверждённое. Наблюдение всё ещё не применяет события автоматически.

`readNativeStoryIdentity` — консервативная проверка возможностей DOM: нужны native ID, явная роль и родитель на самой строке сообщения. Виртуальный ключ, соседняя строка и сгенерированный протокол не заменяют эти поля. Маркер явного корня может выставляться адаптером лишь по подтверждённым native-метаданным; отсутствующий атрибут и строка «null» сами по себе им не являются. Не все версии сайта предоставляют необходимую структуру. Диагностическая проверка history API и внутренний приём пары описаны ниже; получение явной связи из реального транспорта, подтверждение завершения и автоматическое подключение считывателя ещё не реализованы.

Проверка происхождения, квитанций и подменённой копии входит в общий валидатор графа. Совместимы прежние наблюдения без `requestProof`, но они не считаются подтверждёнными новым путём. Обычный снимок квитанции не содержит реплику пользователя. Родство всех редакций индексируется одним итеративным проходом в памяти, вместо пересчёта каждого предыдущего префикса; постоянный индекс базы пока не добавлен.

`tests/story-request-identity.test.ts`, `tests/story-requests.test.ts`, `tests/story-lineage.test.ts` и дополнительные проверки транспорта покрывают явный корень/неизвестность, точный родитель, две вкладки, повтор, невыбранные альтернативы, HTTP-ошибку, прерывание, атомарный откат, ручную правку, reopen, сейф, восстановление и удаление. Цепочка 12 000 узлов — проверка итеративного алгоритма, не обещание скорости всей базы. Установленный пакет дополнительно проверяется на синтетической странице, не в личном аккаунте DeepSeek.

## Стабильные наблюдения и привязка исходной точки RP 01

`observeNativeStoryMessage` принимает проверяемую native-идентичность, точную локальную родительскую редакцию, принятую квитанцию, исходный текст и отдельный признак завершённости. Локальные ID сообщения и редакции назначаются под общей блокировкой библиотеки. Повтор сканирования, reload, восстановление копии и две вкладки находят прежние ID в базе; хеш текста или положение DOM не заменяют идентичность.

Одинаковый native-ключ в одном прохождении сохраняет ID сообщения. Другой текст, завершённость, локальный родитель или новый принятый запрос образуют другую редакцию, если проходят проверки квитанции. Точный повтор ранее наблюдавшегося варианта на той же квитанции возвращает прежнюю запись. Повтор сохраняет существующие кандидаты событий, не добавляет их заново и не меняет выбранную сцену. Частичный и завершённый текст — отдельные неизменяемые редакции, даже если их строки совпадают.

Похожие тексты разных native-сообщений не сливаются. Противоречащие старые локальные ID одного native-сообщения останавливают наблюдение: автоматического объединения нет. Старый источник без `requestProof` не переписывается; при достаточных новых доказательствах сохраняется отдельная подтверждённая редакция. Пользовательскую реплику нельзя молча заменить на той же квитанции: правке нужен новый принятый запрос. Сохранённый источник сам по себе не становится фактом мира или принятым событием.

`readNativeStorySample` снимает текст только при явно переданном вызывающим адаптером признаке завершения именно этой native-редакции. Таймаут стабильности, отсутствие кнопки Stop и HTTP 2xx таким признаком не являются. Неизвестное состояние возвращает `null`. Из копии DOM исключаются размышления, кнопки и добавленные расширением элементы управления; исходная страница не изменяется. Свёрнутый исходный протокол сохраняется в тексте, а восстановленный видимый фрагмент не выдаётся за доказанный завершённый источник. Считыватель не подписан на реальный чат автоматически.

`anchorStoryCheckpoint` — явное внутреннее решение принять сохранённую сцену за исходное состояние после конкретного завершённого ответа сайта либо у подтверждённого корня. Его нельзя вызывать автоматически только потому, что ответ последний на экране. В `baseline.origin.nativeAnchor` сохраняются точный ключ и роль, но не вымышленная родительская редакция или события. Текущее состояние и его редакция должны совпадать с исходным снимком; другой чат, пользовательская роль вместо ответа, незавершённый источник и ручная правка отклоняются.

Привязка допустима только до первого запроса, наблюдения или выбора хроники. Одинаковый повтор не пишет данные и не стирает более позднюю ручную правку. Другая привязка отклоняется; исходное состояние не перемещается задним числом. После привязки новый ход может следовать за внешним родителем без локальной редакции при точном ключе привязки; новая редакция первой реплики после этой точки получает исходное состояние без её прежних последствий. Повтор ответа или правка до этой точки остаются недоступны: предыдущее состояние неизвестно. Это не реконструкция старого чата и не полное решение миграции.

Дополнительное поле origin совместимо с прежними исходными точками без привязки. Оно входит в сейф и копию v2, проверяется вместе с графом и сохраняется при организационном удалении мира. Полное удаление лора убирает его вместе с хроникой. Тексты и имена не попадают в ошибки этих операций.

`tests/story-observer.test.ts` проверяет реальный репозиторий на одноразовых базах: устойчивые ID, конкурентный повтор, редакции и прерывание, кандидаты, неподтверждённые старые записи, неправильные связи, откат записи, reopen, сейф, резервную копию и границы привязки. DOM-проверки и `tests/e2e/story-identity.spec.ts` используют синтетические строки сообщений в Chromium/Firefox. Эти проверки не подтверждают доступность нужных native-полей на живом сайте.

Внутренний контекст до родителя реализован ниже. Строгая диагностика native-связей не заменяет подтверждение завершённости и подключение игрового пути. Текущий адаптер по-прежнему использует прежнюю обработку сцены; безопасный откат перегенерации на реальном DeepSeek пока не объявлен готовым.

## Диагностика структуры истории RP 01

`readNativeStoryHistory` отдельно от прежнего переноса переписки читает только явные ID, роль и родительскую связь. Поддерживаются названия списков и оболочек, уже известные адаптеру переноса; общий декодер не объявляет все эти варианты актуальным контрактом сайта. Текущий узкий native-контракт сверён в итерации 197 и описан отдельно ниже. Номер сообщения, порядок ответа API, похожий текст и единственный последний узел не служат доказательством родства или выбора варианта. Прежний запасной порядок переноса не изменён и в новый декодер не перенесён.

Корень — только явное значение `null`. Число 0 и строка «null» сохраняются как ID. Алиасы `message_id`/`id` и `parent_message_id`/`parent_id` разрешены лишь при совпадении значений после нормализации числового ID. Отсутствующий родитель, противоречащие алиасы, дубли ID даже с одинаковым содержимым, цикл и последовательные одинаковые роли делают весь набор непригодным для автоматического использования. Валидная часть неоднозначного набора не принимается молча.

Родитель за пределами страницы остаётся явной границей, а не объявляется корнем; `has_more` тоже отмечает частичное окно. `ancestry: complete` означает лишь отсутствие потерянных связей в полученном наборе, не завершённый ответ модели и не выбранную ветку. Несколько альтернатив или корней не выбираются автоматически. Общий `completion` остаётся `unknown`, включая поля со значениями, похожими на FINISHED. V4 добавляет отдельный узкий `nativeSnapshot.anchorCompletion`, не меняет смысл старых отчётов и не утверждает принятие ответа по локальной квитанции.

Внутренний page bridge поддерживает явный `NATIVE_STORY_METADATA_REQUEST` для текущего чата. Он делает только GET истории через сохранённый оригинальный fetch; запрос модели не отправляется, поток completion не читается и не заменяется. При переходе со страницы результат отбрасывается. Одновременно разрешён один такой probe, ожидание ограничено пятью секундами. Смена URL даже внутри того же чата не получает старый результат.

`probeNativeStoryHistory` отдаёт через `NATIVE_STORY_METADATA_RESULT` только тип результата и ограниченный отчёт: количество сообщений/связей/границ, фиксированные коды с путями, наличие и типы известных полей завершения. С итерации 178 явная ручная проверка дополнительно включает безопасные счётчики состояний v2, описанные ниже. Не передаются исходный JSON, тексты, размышления, токены, произвольные значения статусов/имена полей и native ID сообщений. ID технического запроса и чата служат адресации ответа. HTTP-ошибка, неверный media type, слишком большой ответ и ошибка чтения различаются без сырого исключения.

Одна операция ограничена 100 000 сообщениями и 30 000 000 байтами; поток истории прерывается при превышении размера даже без Content-Length. Это ограничения диагностического запроса, не размера хранимого мира. В отчёт попадает максимум 40 ошибок при сохранении общего количества; этот предел не связан со старым потолком персонажей. Обход родительских связей итеративный, без рекурсии и повторного обхода каждого префикса.

Probe не запускается автоматически, не записывает историю и не выставляет DOM-маркеры. Ручной экран описан ниже; связь с локальной квитанцией/применением событий ещё не подключена. `tests/story-native-history.test.ts` и `tests/story-native-history-probe.test.ts` проверяют форму, родство, границы, приватность, размер, конкуренцию, навигацию и таймаут. `tests/e2e/story-native-history.spec.ts` выполняет сам исходный bridge в Chromium и Firefox с локальным mock API: это не прогоны установленного MV3 на реальном DeepSeek. Цепочка 20 000 узлов проверяет отсутствие рекурсивного/квадратичного обхода, не нагрузочную готовность всей базы.

### Экран диагностики связи

Путь: **Настройки → Файлы и защита → Проверка работы → Диагностика связи с DeepSeek → Проверить текущий чат**. Нужно открыть чат в активной вкладке. Чтение запускается только кнопкой; открытие настроек само по себе не вызывает probe. При генерации ответа, закрытом сейфе или уже идущей проверке новый probe не запускается. Сообщение `DR_STORY_DIAGNOSTICS` адресуется активной вкладке; результат после смены вкладки/URL отбрасывается. Контентный клиент отдельно проверяет окно, origin, ID проверки и чат, ограничивает ожидание и удаляет временный слушатель. Истёкший поиск вкладки не запускает запоздалую проверку.

Экран различает согласованные связи, неполное окно, противоречия, неподдерживаемый формат и пустую историю. HTTP, размер, чтение, таймаут и отсутствие связи с расширением получают отдельные понятные действия RU/EN. Успешное чтение не показывает «хроника готова»: в V1–V3 выбор редакции и жизненный цикл остаются неизвестны; в V4 отдельный блок описывает только подтверждённый серверный снимок. Связь с принятой локальной отправкой остаётся неподтверждённой. Технические пути/коды, типы известных полей, границы и пагинация раскрываются отдельно. Время обозначает последнюю проверку, не непрерывное наблюдение за чатом.

`readStoryDiagnosticResult` повторно проверяет недоверенную сводку на границе страницы и перед отображением/копированием: строгая форма, ограниченные количества, фиксированные поля/типы/коды и только известные пути схемы. Произвольное имя поля, текст ошибки, неизвестное значение статуса и лишнее поле не пересылаются. Объект пересобирается из разрешённых данных, а не выводится целиком. Копируемый отчёт включает версию диагностики/расширения, время и явное `automaticStoryIngestion: not-connected`; не включает request/chat/native ID, адреса, лор, ответы, размышления и ключи. Это описание возможностей, не аутентифицированное доказательство родства.

#### Безопасные счётчики состояния, диагностический формат v2

Живой отчёт пользователя 10.10.2026 прочитал 144 явные связи без ошибок: `ancestry: complete`, один корень, нет границ/пагинации; поле `status` встречается в 144 сообщениях как строка. В v1 нет её значения, поэтому отчёт не подтверждает ни выбранную редакцию, ни значение завершённости. Это наблюдение структуры конкретного полученного окна, не подтверждение всех возможных сообщений сервера.

В явной ручной проверке теперь включено `collectStatuses: true`; обычный внутренний декодер без этой опции сохраняет отчёт v1. V2 добавляет `statusCounts` — фиксированные строки `{ field, role, state, count }` для собственных полей `status` и `message_status` и ролей `user`, `assistant`, `unknown`. Собственные значения роли обрабатываются точно как в декодере, неизвестные/отсутствующие роли не раскрываются. Учтены все записи окна, включая записи с недопустимыми связями; это счётчики наблюдений, а не число принятых или выбранных ответов.

Разрешённые точные строки: `FINISHED`, `COMPLETED`, `STOPPED`, `INTERRUPTED`, `ERROR`, `FAILED`, `STREAMING`, `PENDING`, `WAITING`, `GENERATING`, `RUNNING`, `CANCELLED`, `CANCELED`, `IN_PROGRESS`. Это **список безопасных литералов для диагностики, не перечень доказанно поддерживаемых DeepSeek состояний и не описание их смысла**. Другие строки становятся `unrecognized-string`, остальные типы — `non-string`; исходные значения не обрезаются, не нормализуются и не выводятся. `finish_reason`, даты и булевы поля по-прежнему передаются только как счётчики типов, без значений.

Максимум 96 строк (2 поля × 3 роли × 16 категорий), детерминированный порядок и положительные количества. Принимающая сторона проверяет точную форму, допустимые литералы, отсутствие дублей и совпадение количества строковых/нестроковых наблюдений каждого поля с `completionFields`; суммарное количество поля не может превысить размер окна или 100 000. Оба формата v1/v2 читаются; в копируемом отчёте версия соответствует безопасному результату, для ошибок без сводки остаётся v1.

Счётчики раскрываются только в технических подробностях RU/EN. `completion: unknown` и `automaticStoryIngestion: not-connected` не меняются, даже если все 144 состояния окажутся `FINISHED`. Проверка по-прежнему запускается только кнопкой и не читает completion-поток, не отправляет запрос модели, не записывает историю, не выбирает ветку и не применяет события. Следующий шаг — проверить коды из нового живого отчёта и точную связь конкретной отправки с редакцией ответа. `tests/story-status-summary.test.ts` дополнительно проверяет приватность, обратную совместимость и подмену счётчиков.

Отчёт можно скопировать одной кнопкой; при недоступном буфере появляется поле только для чтения с выделением текста. Результат хранится только в состоянии экрана, не в базе/резервной копии, и сбрасывается при новом запуске или закрытии экрана настроек. Проверка не меняет черновик, сцену, лор, режим DeepThink и не отправляет запрос модели. `tests/story-diagnostics*.test.*` проверяют безопасность, маршрутизацию, смену области, таймаут и UI. Браузерные сценарии проверяют RU/EN, клавиатуру, 320/760 px, копирование/запасное поле и автоматическую доступность в Chromium/Firefox; установленный Chromium MV3 отдельно проходит полный путь panel → content → bridge на локальном mock DeepSeek. Это не живой аккаунт и не проверка установленного Firefox.

SHA-256 UTF-8 текста загруженного клиентского файла: `F0953F4D9054DB295B269914BF3E39FDB2D82D70639356FF52E282BB8C9D1A9F`. ### Серверный снимок

`readNativeStoryServerSnapshot` сначала сохраняет прежние проверки графа и v3 reply probe, затем допускает только узкую оболочку `code: 0`, `data.biz_code: 0`, `data.biz_data.chat_session` и `chat_messages`. `chat_session.id` должен точно соответствовать запрошенному чату. Строки native-сообщений требуют собственные `message_id`, `parent_id`, роли `USER`/`ASSISTANT`. Совместимые алиасы старого декодера не превращаются в подтверждение текущего native-формата.

Ветку задаёт только `chat_session.current_message_id`; родительская цепочка обходится по проверенным связям до явного корня. Нет fallback на максимальный ID, последний элемент, единственный лист или похожий текст. Отсутствующий/неподходящий указатель, потерянный префикс, пагинация и противоречивый граф не разрешают использование полной выбранной цепочки. Полная цепочка одной ветки может существовать при недостающем родителе другой ветки; это не скрывает общую частичность диагностического окна.

Для точно найденного ответа `FINISHED` плюс `has_pending_fragment: false` подтверждают завершённый серверный снимок только при отсутствии противоречащего `quasi_status`/`incomplete_message`. `WIP` означает генерируемый снимок, `INCOMPLETE`/`TIMEOUT` — прерванный, `CONTENT_FILTER`/`CONTEXT_LENGTH_EXCEEDED` — непригодный для автоматического принятия. Незнакомое значение, отсутствие нужных полей и конфликт остаются `unknown`, пользовательская реплика — `not-applicable`. Клиентский fallback неизвестного статуса на OK не повторяется.

V4 добавляет строго пересобранную `nativeSnapshot` с фиксированным контрактом, совпадением чата, отношением anchor к серверной ветке, полнотой цепочки, количеством сообщений и состоянием ответа. Native ID/исходный текст остаются внутри page bridge и в копируемый отчёт не входят. Общий `completion` по-прежнему `unknown`: он не маскируется доказательством принятого локального обмена. Список безопасных статусных литералов расширен на проверенные выше точные коды; прошлые `unrecognized-string` не переинтерпретируются.

**Серверная ветка и выбранный на странице вариант — не одно и то же.** Публичный клиент умеет переключать локальный `currentChildIndex`, который может отличаться от серверного `current_message_id`. Проверка показывает эту границу явно; не применяет событие и не изменяет активную линию. Существующие guards чата, URL, anchor, генерации и сейфа остаются обязательны.

### Пассивные XHR/SSE-метаданные

Текущий публичный клиент читает накопительный XHR `responseText` через download-progress. Для распознанной асинхронной обычной отправки bridge читает только новые части `text/event-stream`, не меняет исходный ответ и не посылает дополнительных completion-запросов. Для Fetch поток не клонируется/не потребляется; отсутствие этого наблюдения остаётся неизвестностью, а не успехом.

`ready` требует два разных безопасных числовых native ID: `request_message_id` и `response_message_id`. Они связываются с точными метаданными этого запроса, а не с UUID/ID, повторённым моделью в тексте, или SSE-полем `id`. `finish` — отдельный wire-маркер; `close` — закрытие протокола. Ни один из них сам по себе не доказывает успешное состояние сообщения, выбранность или применимость событий. Отмена, superseded XHR, ошибка сети, неполный/незнакомый протокол и `hint`/`toast` фиксируются закрытыми кодами без текста сервера.

Разбор допускает LF/CRLF/CR и границы в любом месте чанка. Максимум 30 000 000 символов потока, 1 000 000 символов кадра и 2048 символов ready JSON — защитные лимиты одного наблюдения, не предел хроники/персонажей. Превышение выключает только новый наблюдатель; исходная доставка ответа не меняется. Поддержаны только запросы с уже проверенными явными `chat_session_id` и `parent_message_id`; прочие формы не угадываются.

`NATIVE_STORY_STREAM` содержит только локальный request ID, точные метаданные маршрута, native-пару, фазу и фиксированную причину. Валидатор запрещает лишние поля и несогласованную пару. В итерации 197 сигнал ещё не сохранялся; итерация 198 подключила его к зарегистрированному журналу отправки, описанному выше. Shape/origin/page bridge не являются аутентификацией. Драйвер обязан сопоставить его с сохранённой принятой квитанцией, исходной пользовательской репликой, native-редакцией и реально выбранным вариантом до атомарной записи/принятия.

### Остаток RP-01

Подключить новый игровой путь и policy/UI принятия, не оставляя параллельные старые прямые изменения сцены; разделить добавленный контекст и оригинальную реплику по сохранённой отправке, а не по произвольному текстовому маркеру; проверить правку ранней реплики, три варианта, возврат, reload и две вкладки. Проверенные источники ещё не являются принятыми фактами. Production-миграция, автоматическая хроника и оптимизация RP-04/RP-05 не включены. Зелёные тесты снимка/потока не закрывают восемь audit todo.

## Приём пары сообщений по конкретному запросу RP 01

`matchNativeStoryExchange` проверяет внутренний пакет драйвера, а `observeNativeStoryExchange` сохраняет его источники. Пакет должен содержать принятую локальную квитанцию с известным контекстом, ID чата, строгие native-метаданные, явную связь `link` с пользовательским/ответным сообщением, исходные образцы и отдельное свидетельство состояния именно этой редакции `terminal`. Единственный найденный потомок, порядок истории или повтор ID запроса в модельном JSON не заменяют `link`. Драйвер обязан получить связь из native-транспорта конкретной отправки; на реальном сайте он ещё не реализован. Это внутренний контракт, не предположительное описание полей DeepSeek.

Проверяются область чата, точный родитель квитанции, роли и родство пары, отсутствие дублей/циклов в метаданных, соответствие образцов и стабильность уже привязанного источника. Граница страницы допустима только при известном локальном родителе или явной исходной привязке. Нельзя переиспользовать внешний ID предка как новое сообщение. Старые неоднозначные ID, родитель без доказанного происхождения и квитанция без сохранённого контекста дают паузу, не автоматическое исправление прежних записей.

`terminal` требуется и для полного, и для частичного/прерванного ответа. Он связывает локальный запрос, native-сообщение, состояние и SHA256 канонического образца, захваченного при известном состоянии. Хеш защищает от использования старого сигнала с новым текстом, но сам не подтверждает завершение и не аутентифицирует страницу. Известный жизненный цикл должен отдельно установить рабочий адаптер; отсутствие кнопки остановки или строка FINISHED не объявляются таким доказательством. Связь и хеш пакета не добавляют новый тип записи или сохранённую криптографическую аттестацию.

Вход копируется до хеширования/ожидания блокировки. Под библиотечной блокировкой повторно проверяется сохранённая квитанция, назначаются устойчивые локальные ID и одним атомарным обновлением записываются реплика и ответ. Сбой после первой строки откатывает обе. Конкурентный повтор из двух вкладок и повтор полного пакета после reopen возвращают прежние редакции; ранее сохранённые кандидаты не стираются. При повторе ответа используется уже сохранённая пользовательская редакция, без новой реплики; если её образец передан, текст должен точно совпасть. Ранняя правка требует новой явной квитанции, а не подмены пользовательского текста внутри прежнего запроса.

Частичный/прерванный ответ остаётся наблюдением, непригодным для выбора; поздний полный образец становится отдельной редакцией того же сообщения. Сохранение пары не выбирает ветку, не принимает события, не изменяет текущую сцену/анкеты/канон и не запускает изображения или модель. Поздний принятый ответ можно сохранить как исторический источник после ручной правки или смены выбранной линии, но применение по-прежнему требует отдельной проверки конфликтов. Архивная область и удалённый лор не получают новых источников; закрытый сейф блокирует операцию.

Пауза возвращает только фиксированный код и путь поля без исходного текста, имён, реальных request/chat/native ID или секретов. Она не записывает строки. Формат story остаётся 1, production IndexedDB — 2; источники используют прежний сейф и полную резервную копию. Чтение и проверка пока загружают все строки нужных типов; постоянные индексы и измерения большой истории остаются RP-07.

`tests/story-exchange.test.ts` проверяет 64 сценария сопоставления, ошибок, конкуренции, атомарного отката, частичных редакций, повтора/ранней правки, поздних результатов, старых записей, сейфа, копии и удаления. `tests/e2e/story-exchange.spec.ts` проверяет настоящие IndexedDB/Web Locks, две вкладки и reload на синтетических RU/EN данных в Chromium/Firefox. Явные `link`/`terminal` там задаёт фикстура: это не доказательство наличия рабочих сигналов на живом DeepSeek или готовности установленного MV3. Новые внутренние API ещё не вызываются sender/content RPC/UI игры.

## Контекст состояния до родителя запроса RP 01

При подготовке новой квитанции `prepareStoryRequest` пересчитывает состояние до `parentRevisionId`, а не до последней выбранной вершины. В `request.context` сохраняются `algorithmVersion: 1` и отсортированные ID уже принятых событий именно этого префикса. Подготовка квитанции и фиксация разрешений атомарны. Источники, исходная точка и события неизменяемы, поэтому полный снимок состояний и текст запроса не дублируются в каждой квитанции.

Обычный ход включает последствия завершённого родителя. Повтор ответа заканчивает контекст на пользовательской реплике: отменяемый ответ и все его потомки исключены вместе с числовыми изменениями, короткой историей показателей, присутствующими и собеседниками. Ранняя правка пользовательской реплики получает состояние до неё. Из явно привязанной исходной точки можно создать другую первую реплику после точки; при неизвестной привязке эта операция останавливается.

`projectStoryRequestContext` чисто реконструирует сохранённый префикс; `readStoryRequestContext` читает его под блокировкой и проверяет принадлежность квитанции переданной ветке. Последующий выбор другого варианта, разрешение/отмена кандидата, ручная правка текущей сцены и результат HTTP-доставки не меняют сохранённый контекст. Повтор подготовки с тем же ID возвращает прежнюю квитанцию и не вычисляет её заново по новым разрешениям. Это историческое чтение, в том числе архивного мира, а не разрешение отправить устаревший запрос: перед реальной отправкой остаются необходимы проверки активной области и версии.

Старые квитанции без `context` остаются читаемыми в хронике и резервной копии. Контекст для них неизвестен: чтение сообщает `story-request-context-missing`, а повтор подготовки не подставляет сегодняшнее состояние вместо утраченного снимка. Новые квитанции всегда сохраняют поле. Неизвестная версия, лишние поля, повторные/несортированные ID, событие чужого чата или за пределами родительской цепочки отклоняются. Общий граф также пересчитывает сохранённые разрешения от исходной точки: пропуск обязательного события и несовместимое состояние до изменения обнаруживаются до восстановления копии.

Для проверки родства используются уже построенные интервалы редакций; исторический префикс не обходится заново для каждой квитанции. Пересчёт одинакового набора разрешений одной исходной точки переиспользуется внутри одного прохода проверки, но ссылки каждой квитанции всё равно проверяются отдельно. Чтение пока загружает все строки нужных типов, а списки разрешений повторяются между запросами. Постоянный индекс, разделяемые версии разрешений, компактизация и измерения длительных историй остаются RP-07; это не заявление о неограниченной скорости или размере базы.

`storyRequestCharacterScene` создаёт отдельное представление для существующего `characterInstruction`: состояние, присутствующих и собеседников из сохранённого префикса, стабильную редакцию запроса и время подготовки. В нём нет `lastReply`, progress, notice или состояния изображений из более поздней сцены. Мутация возвращённого объекта не меняет снимок или базу. Представление не записывается в текущую привязку чата, не запускает модель и не принимает события.

Граница этой части — сыгранное состояние персонажей. Общий лор, ручные анкеты, старые записи памяти без области и recent messages обычного сборщика ещё не фильтруются по новой линии. Платные/графические последствия и автоматическая отправка не подключены. Поэтому наличие внутренней проекции не означает, что весь реальный запрос уже очищен от альтернативной памяти.

`tests/story-request-context.test.ts` проверяет обычный ход, повтор раннего ответа и реплики, первую реплику после корня/ответа-исходной точки, зафиксированные разрешения, присутствующих/собеседников, числовую историю, конкурентные повторы, ручную правку, подменённую копию, атомарный сбой, reopen, сейф, совместимость и удаление. `tests/e2e/story-request-context.spec.ts` проверяет существующий построитель character prompt на синтетических RU/EN данных в Chromium и Firefox; это не отправки в живой DeepSeek.

## Слои памяти

| Слой | Что хранится | Что не должно происходить |
| --- | --- | --- |
| Канон мира | Исходный и подтверждённый лор, личности, правила, ручные исправления | Событие одной альтернативы не становится общим правилом мира |
| Прохождение | Одна продолжающаяся история в одном или нескольких чатах | Новый чат не означает автоматически новое или прежнее прохождение |
| Ветка | Выбранная последовательность редакций внутри прохождения | Альтернативные последствия не смешиваются |
| Сообщение и редакция | Наблюдавшийся текст, родитель, запрос, завершённость, выбранный вариант | Похожий текст не доказывает тождество сообщений |
| Событие | Подтверждённое изменение с источником и участниками | Предложенный вариант действия не считается сыгранным |
| Текущее состояние | Пересчитываемое состояние выбранной линии | Состояние не заменяет журнал событий |
| Предложение | Ещё не принятый факт или изменение анкеты | Предложение не влияет на запрос как подтверждённая память |

Канон остаётся общим. Цель «починить часы», факт передачи ключа, положение героя и изменение отношения могут относиться только к конкретному прохождению. Названия, возраст и исходный текст не исправляются миграцией. Неясное происхождение старого факта отмечается как `legacy-unclassified`, а не задним числом объявляется каноном или событием.

## Идентификаторы и связи

Записи получают неизменяемые локальные ID. Имя, псевдоним, язык интерфейса, порядок карточек и хеш текста не являются идентификатором личности. Два персонажа с одним именем остаются разными записями. Переименование сохраняет ссылки. Удаление требует проверки ссылок и выбранной области удаления.

Таблица задаёт полный целевой контракт. Реализованная часть перечислена выше; остальные связи должны быть добавлены до автоматического применения последствий ответа.

| Запись | Обязательная связь |
| --- | --- |
| Прохождение | `playthroughId`, `worldId` или явный режим без мира |
| Ветка | `branchId`, `playthroughId`, исходная точка; подтверждённый родитель либо явная неизвестность |
| Сообщение | `messageId`, роль, чат сайта, область истории |
| Редакция | `revisionId`, `messageId`, родительская редакция, наблюдавшийся внешний ключ, завершённость |
| Запрос | `requestId`, чат, область истории, родительская редакция, версия состояния при отправке |
| Событие | `eventId`, область истории, исходная редакция, порядок, участники, операции, происхождение |
| Проекция | Область истории, исходная точка, выбранная вершина, версия алгоритма, применённые события |
| Предложение | Область истории, источник, ожидаемые версии затрагиваемых записей, статус решения |

Внешний ключ сайта сохраняется отдельно от локального ID. Для ответа сопоставляются локально принятый запрос, родитель, выбранная редакция и прохождение. Модель не выбирает базу, чат или ветку назначения. Если сайт не даёт надёжных связей, зависимые изменения приостанавливаются; похожий текст и число сообщений не заменяют проверку.

Компактный ключ вроде `p1` в одном запросе может ссылаться на локальный ID через сохранённый список участников этого запроса. Повторное использование `p1` в другом запросе не связывает личности. Неоднозначное имя требует выбора, а действительно новый персонаж сначала получает проверяемое предложение или локальную запись по явно разрешённому сценарию. Технические ключи не попадают в обычное описание анкеты.

## Редакции и последствия

Одна редакция может быть наблюдаемой, незавершённой, завершённой или восстановленным видимым фрагментом. Состояние наблюдения хранится отдельно от принятия событий. Восстановленный фрагмент не доказывает невидимое окончание ответа.

У события есть отдельные признаки проверки и активности. Проверенное событие отменённой альтернативы сохраняется в хронике, но не участвует в выбранной проекции. Повторная доставка события с той же локальной идентичностью не применяется повторно. Хеш служит проверкой содержимого, а не единственным ключом применения.

При смене ответа порядок действий такой:

1. Надёжно определить выбранную редакцию и её родительскую цепочку.
2. Исключить последствия невыбранной редакции и зависимых потомков.
3. Пересчитать проекцию из исходной точки и принятых событий выбранной цепочки.
4. Сохранить новую выбранную вершину и проекцию одной атомарной операцией.

Нельзя просто принять прежний `base` после перегенерации: это обход защиты от устаревших запросов, а не поддержка альтернатив. Ручные изменения имеют собственный источник и область действия. Откат модельного ответа не должен стирать ручной канон; несовместимое ручное изменение внутри ветки требует явного конфликта.

Хроника не обрезается до последних 20 событий. Ограничивать можно страницу интерфейса, выдачу для поиска и объём запроса. Повторное сканирование, reload и две вкладки должны давать одно применение. Производные кэши и сводки имеют версию и перестраиваются после смены выбранной цепочки.

## Обновление полей и проверка ответа

RP-02 вводит разные операции: оставить прежнее (`keep`), установить (`set`), очистить (`clear`). Отсутствие поля означает оставить прежнее. Пустая строка не является неявной командой очистки. Цель персонажа и постоянные сведения его анкеты — разные поля.

Сначала проверяется принадлежность всего ответа. Только после этого независимые корректные изменения можно отделить от ошибочных. Создание персонажа, ссылки на него и связанное событие образуют зависимую группу: нельзя сохранить только её половину. Ручные и импортированные сведения не заменяются модельной оценкой без нужного разрешения.

Исправление служебных данных не переписывает рассказ. Дополнительный запрос ограничен, связан с исходной редакцией и не запускается бесконечно. Схема диагностики содержит этап, путь поля, правило, результат и счётчики, но не полный лор, ответы, секреты или ключи сейфа.

## Совместимость и исходная точка старой базы

Текущая база приложения использует Dexie версии 2, записи `records` и фотографии `photos`; переносимые копии имеют собственную версию формата. Версия контракта, версия схемы IndexedDB и версия экспортного файла независимы. RP-00 и первая часть RP-01 не повышают версию установленной базы.

Старое `characterScenes` — известное текущее состояние, а не история всех предыдущих действий. При переходе оно становится исходной точкой с `historyBeforeBaseline: unknown`. Из него не создаются события, награды и вымышленные сообщения. Старые короткие журналы сохраняются в снимке, но не объявляются полной хроникой.

Для каждой пары старой привязки чата и сохранённого мира создаётся отдельная исходная точка. Уже имеющиеся связи продолжения и снимки сохраняются; автоматическое объединение историй допустимо только после проверки этих связей. При неизвестной родословной чаты не сливаются по названию мира, похожим героям или тексту. Мир без привязанного чата не получает вымышленное прохождение.

Полный исходный снимок миграции должен сохранять старые записи и служебные задания. Первая часть RP-01 лишь добавляет исходную точку состояния и оставляет прежние строки на месте; переключения активного формата и полной production-миграции ещё нет. Служебное задание не превращается в факт истории. Исходные записи памяти с неясной областью остаются доступны в совместимом режиме; автоматический перенос в новый канон запрещён.

## Порядок безопасной миграции

1. Проверить поддерживаемые версии и доступность сейфа. При закрытом сейфе оставить базу нетронутой и дождаться разблокировки.
2. Получить согласованный исходный снимок записей, настроек, привязок и ссылок на изображения. Для переноса самих фотографий нужен снимок их содержимого и проверка целостности; одна ссылка его не заменяет.
3. Подготовить и проверить новый формат отдельно от активного. Шифрование, расшифровку и тяжёлые вычисления завершить до транзакции IndexedDB.
4. Под общей блокировкой библиотеки повторно проверить источник, конфигурацию сейфа и целевой набор. При конкурентной правке остановиться и подготовить заново, не отменяя правку пользователя.
5. Одной транзакцией записать новые исходные точки, снимок, манифест и указатель активной версии. Любой сбой откатывает всю незавершённую операцию.
6. При повторном запуске проверить версию, контрольные суммы, состав и расшифрованное содержимое уже готового набора. Наличие одного маркера «готово» не является доказательством целостности.
7. Не удалять старый формат до проверенного чтения и восстановления. Для порционной миграции крупных баз использовать возобновляемое промежуточное поколение; оно не становится активным до финальной проверки.

Новые исходные точки, события, сводки и индексы с содержимым истории защищаются тем же сейфом. Не создавать открытый поисковый индекс поверх зашифрованной памяти. Внутренний снимок помогает пережить сбой миграции, но исчезнет вместе с профилем браузера: он не заменяет внешнюю резервную копию.

## Постоянные проверки RP 00

`tests/story-audit-baseline.test.ts` воспроизводит восемь находок аудита. Девять проверок текущих проблем включают отдельные RU/EN сценарии поиска; ещё четыре проверки контролируют синтетические миры и защиту назначения. Восемь `it.todo` — явно незакрытые критерии RP-01, RP-02, RP-03 и RP-05. Зелёный прогон воспроизведения не означает исправление бага. На соответствующем этапе критерий превращается в исполняемый тест нового рабочего пути, а проверка старого сбоя заменяется целевой регрессией только вместе с исправлением.

| Находка | Исправляющий этап |
| --- | --- |
| Новая анкета ограничена внешностью и характером | RP-03 |
| Существующая анкета не дополняется | RP-03 |
| Альтернативный ответ не принимается после сохранённого | RP-01 |
| Ошибочный элемент отклоняет весь блок | RP-02 |
| Местоимения без связей не находят нужную запись | RP-05 |
| Фокус на персонаже после первых 40 не достигает анкеты | RP-03 |

| Анкеты вытесняют память, не весь контекст входит в показанный бюджет | RP-05 |

`tests/fixtures/story-worlds.ts` содержит независимые RU/EN варианты: обычный мир, фантастику, двух героев, совпадающие имена и псевдонимы, 1000 персонажей, два различающихся состояния истории. Подробные анкеты и большой текст проверяют объём без личного лора пользователя. Наличие фикстуры на 1000 персонажей не является нагрузочным измерением или заявленным пределом.

`tests/story-migration-rehearsal.test.ts` проверяет старую обычную и зашифрованную базу через настоящий репозиторий, Dexie, fake-indexeddb и WebCrypto. Только тестовый подкласс добавляет таблицу репетиции версии 3. Проверяются сохранение и восстановление исходных строк, текстов и встроенных данных изображения, независимость исходных точек, отсутствие выдуманных событий, отмена транзакции в двух местах, повторный запуск после reopen, конкурентные планы и правки, включая правку с последующим возвратом исходника, закрытие сейфа, неполный или подменённый целевой набор, попытка заменить шифротекст открытыми данными, неправильная запись и потерянная ссылка на мир.

Репетиция записывает новые исходные точки и манифест, но не переключает приложение на хронику и не удаляет старые записи. Она не проверяет реальное завершение процесса браузера, заполненный диск, перенос байтов отдельного Blob-хранилища, внешнюю резервную копию или порционную миграцию большой базы. Эти сценарии остаются критериями следующих этапов. При подключении production-миграции тесты должны проверять её настоящий путь, а не только тестовый прототип.

Запуск: `npm test -- tests/story-audit-baseline.test.ts tests/story-migration-rehearsal.test.ts`. На RP-01 сюда добавляются настоящие события, редакции, выбор линии и откат; текущие проверки происхождения и защиты назначения остаются обязательными.
