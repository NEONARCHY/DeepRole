# RP331 — восстановление отправки памяти после перехода

## Задача и границы

Продолжение неуспешной живой проверки RP330. В ней записи были выбраны, но
DeepSeek получал вопросы без памяти. Семь исходных фактов и восемь gold-вопросов
из `benchmarks/rp330-live-plan.json` не менялись. Старый неуспешный результат
остаётся в `RP05-LIVE-LONG-RESULTS-20261019.md`.

Ниже — причины, воспроизведённые на установленной MV3 с синтетическим API.
Это ещё не доказательство исправления всех причин в личном DeepSeek: после
обновления установленной копии нужен отдельный живой повтор.

## Что исправлено

1. Отклонённая навигация оставляла `navigationTask` rejected. Следующие
   запросы снова получали ту же ошибку даже после явного восстановления игры.
   Теперь текущий запрос по-прежнему отклоняется, а ошибка отработанной очереди
   не блокирует последующие. Более новая очередь перехода не затирается.
2. Плашка старого чата исчезала после промежуточного reload раньше завершения
   активации/запуска игры. «Продолжить здесь» теперь выполняется через общую
   `sceneQueue`: следующая отправка ждёт всю операцию. Чужая страница/мир всё ещё
   отклоняют устаревшее действие; active-tab guard не ослаблен.
3. Поздняя XHR-квитанция вызывает `resetPresentation()`. Раньше этот сброс
   проверки интерфейса отменял одновременно уже начатый native GET следующего
   parent, хотя URL, чат, мир и base совпадали. В red-прогоне зафиксированы
   `preparation=true`, `epochSame=false`, остальные scope-проверки true.
   Теперь parent/edit не зависит от UI epoch. Обычная проверка отображаемого
   ответа всё ещё отклоняет сброшенный/старый proof и не получает права записи.
4. Изменённый checkpoint/profile base отклоняется до commit. После такого
   конкретного отказа подготовка один раз перечитывает сохранённую библиотеку
   и проверяет тот же native parent. URL/мир/binding/выбранная сцена и право
   текущего writer проверяются заново. Чужой scope, закрытый vault, неизвестная
   схема, ручные конфликты и прочие ошибки не превращаются в разрешение записи.

Повторяется только локальная подготовка до отправки. Модельный запрос не
повторяется автоматически. Старые ответы/история и пользовательский лор не
переписываются. При настоящем отказе и выключенной strictMemorySending прежний
режим отправки без памяти с предупреждением сохранён.

## Доказательства до исправления

  `0B68AF2D7E21A76205BA451629F65A7BFD3DDEC6480D13943B098B0D94D5C5C8`
  распакован в отдельную `.output/rp331-baseline`; тот же новый runtime-тест
  `rejected-navigation/fetch/en` падает: второй POST содержит только вопрос,
  без текста памяти. Исходный ZIP не менялся.
- Независимый `stale-parent/fetch/en` падает при пропущенном уведомлении о
  сохранённой правке анкеты. Затем green требует свежую анкету в POST и её
  сохранность в DB, а не просто отсутствие ошибки.

  код — `story-native-line-unavailable`; общий UI-текст не доказывал timeout.
- Два новых unit-теста упали до изменения клиента: UI reset мешал parent,
  изменение base ошибочно считалось непригодной native history. После исправления
  они проходят; четыре дополнительных теста сохраняют отказ при world/chat/URL/lock.

Локальные red traces: `test-results-rp331-baseline-red`,
`test-results-rp331-stale-red`, `test-results-rp331-xhr-cause`.

повторением только успешных сценариев. Во время диагностики временно добавлялся
