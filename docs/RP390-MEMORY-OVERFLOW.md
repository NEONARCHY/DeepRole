# RP390 — переполнение памяти и отказ сохранения реплики

Ожидания закреплены 17 ноября 2026 до первого запуска. RP389, изолированный
Edge, вымышленные записи и синтетические ответы. RU/Fetch и EN/XHR.
Проверяется локальный ограничитель, не текущий лимит живого DeepSeek.

Восемь новых сценариев: два языка × четыре случая.

1. **memory-only**: обязательные записи сами превышают 40 000 единиц UTF-16,
   реплика короткая. Отказ до POST, исходный текст сохранён. Через штатную
   «Подключённую память» отключить одну большую запись. Запись не удаляется,
   мир/анкеты/память игры не переписываются, новый чат ещё не активируется.
   Повтор отправляет короткую реплику, оставшиеся записи и сцену целиком.
2. **memory-reload**: то же, но после изменения переключателя — reload.
   Исключение остаётся действующим, перенос подготовлен. После успешной первой
   пары следующий ход тоже исключает запись; повторное чтение не создаёт дублей.
3. **session-blocked**: при отказе по длине запись копии в session RAM
   намеренно падает. POST отсутствует; видна понятная ошибка сохранения и
   точная реплика для копирования. Нельзя обещать сохранность после reload:
   нужно явно попросить скопировать текст перед уходом. После восстановления
   хранилища ручной короткий повтор проходит один раз.
4. **session-send**: аналогичный сбой при сохранении допустимой первой реплики
   до POST. Нельзя отправить без сохранённой копии или применить перенос.
   Старый текст доступен; набранный одновременно новый черновик не заменяется
   (EN); RU проверяет восстановление пустого редактора.

В обоих случаях сбоя реальная session.set отклоняется только для конкретной
записи восстановления; счётчик доказывает, что отказ сработал. После снятия
сбоя — обычная UI-отправка, проверка первой пары, следующего хода, старого чата
и reload. Никаких ручных записей фактов или отправок в старый чат (он даёт 403).
Предупреждение проверить на 320×470 в обеих локалях. Не ослаблять ожидания.

## Что обнаружено и исправлено

Первая команда baseline не запустилась: `npx.cmd` разобрал `|` в grep как
shell pipe. Повтор выполнен напрямую через Node 24 и Playwright CLI. Первый
браузерный baseline: четыре случая session RAM подтвердили отсутствие
предупреждения; четыре memory остановились на неверном вложенном локаторе.
Локатор исправлен; для асинхронного переключателя заменён немедленный
`uncheck` на click с ожиданием исчезновения записи. Ожидания не изменялись.
Контроль окончательного теста на прежней RP389 отдельно воспроизвёл сбой:
`test-results-rp390-old-build-control`, запись остаётся подключённой.

Причина memory: новый native chat ID принимался за уже подключённую игру.
Переключатель создавал binding до принятия первого хода, а следующие чтения
брали старый общий выбор памяти. Теперь выбор хранится в session RAM текущего
переноса, переживает reload, изолирован токеном и применяется атомарно вместе
с успешным первым ходом. Отмена/новая попытка очищает его. Исходные записи
не удаляются и не переписываются.

При отказе сохранения исходной реплики показан отдельный текст с копией в
памяти страницы. Сообщение остановлено до POST; пользователь предупреждён
скопировать оригинал перед уходом/reload. Новый черновик остаётся нетронутым.
Успешный ручной повтор снимает уведомление своей попытки.

Первый прогон исправлений: memory 4/4, session дошли до проверки геометрии
и выявили уход плашки выше экрана. Уведомление закреплено относительно окна,
внутри доступна прокрутка. RU/EN при 320×470 и шрифте 125% проверены по снимкам.
