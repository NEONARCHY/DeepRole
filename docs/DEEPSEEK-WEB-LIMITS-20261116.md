# Проверка ограничений веб-чата DeepSeek — 16 ноября 2026

## Перенос с главной RP360

RP359 не показывал действие переноса после HTTP 302 со старого
адреса на главную. RP360 предлагает выбрать сохранённую игру в
«Мир и сцена». Выбор показывает локальную сцену. Подключение готовит
первую реплику в открытой вкладке. Старая привязка действует до
подтверждённого ответа на ручную отправку.

Стенд подставлял старый URL, ответ 302, главную страницу и ответы API.
В Edge оба сценария прошли с двумя играми и разными способами отправки
первой реплики (fetch и XHR). Игра, которую использовали только для
предпросмотра, сохранила все записи. Клиентский путь продолжения
из старой страницы остаётся доступен при наличии исходного адреса.

## Проверка длины RP359

17 ноября на реальном DeepSeek с RP362 один запрос длиной 40 000 единиц
UTF-16 был принят (HTTP 200 и штатное завершение потока). В итоговом
запросе были 35 281 единица реплики, 4 702 единицы контекста с лором и
памятью и 17 единиц разделителя. При 40 001 сетевого запроса к модели
не было, а исходная реплика восстановилась посимвольно.

DeepRole проверяет готовый текст перед отправкой по локальному пределу
40 000 единиц UTF-16. Считаются все части сообщения, включая память и
внутренний разделитель. JSON-экранирование и байты вложений в текстовый
лимит не входят. Проверки на 39 999 и 40 000 проходят, на 40 001
запрос останавливается. Это локальный порог, выбранный по сообщениям
о лимите веб-чата, точный серверный порог ещё не измерен.

Тест первого хода после переноса использует реплику 39 999 символов.
Вместе с лором и памятью она превышает предел. Модельного запроса
в новом чате нет, строки хранилища прежние. В одном сценарии редактор
восстанавливает исходную реплику целиком, в другом остаётся введённый
позже черновик и для исходной реплики открывается поле для копирования.
После сокращения реплики тестовый новый чат получает сохранённую
сцену и лор и становится активным после подтверждения.

## Исправление RP358

При первом запросе переноса получение HTTP 200 больше не применяет
снимок. DeepRole ждёт подтверждаемую пару ID в событии ready, затем
finish и close без сигнала повтора. Проверка выполняется в fetch и XHR
для запросов переноса. Остальные запросы используют прежний путь.

Браузерный тест отказа внутри HTTP 200 проверяет, что после перезагрузки
снимок без отметки применения, новый чат без привязки и прежний чат
активен. Сценарий проходит на RU через fetch и на EN через XHR.
На стенде также подтверждён успешный перенос с уже выделенным адресом
нового чата до отправки. Живой ответ DeepSeek пока не проверялся.

## 17 ноября — проверка переноса RP357

Проверена опубликованная Chromium-сборка из коммита `12b9ac5`. Все 26 прежних браузерных сценариев переноса и 96 выбранных тестов Vitest прошли. TypeScript проверен. Браузер использовал отдельные профили Edge и синтетические ответы. На живом аккаунте формат отказа и порог длины остаются неизвестны.

| Сценарий | Результат RP357 |
| --- | --- |
| Старый URL открывается, история отвечает 403, переписки и поля ввода на странице нет | «Мир и сцена → Продолжить из сохранённой памяти» открывает предпросмотр и новый чат без отправки в старый. Снимок ждёт ручной реплики. В первом запросе есть последняя локальная сцена и лор, после принятия меняется активный чат. Незавершённая реплика из старого журнала исключается. Прошло на 320 px в RU/EN. |
| Новый чат вернул HTTP 429 | Старый чат остаётся активным, новый не привязывается, снимок остаётся неприменённым. |
| Первая реплика в 39 999 символов с локальной памятью превысила лимит стенда | Итоговый промпт ушёл целиком: 45 612 символов в RU и 45 627 в EN. После HTTP 413 новый чат не привязался даже после обновления страницы. До отправки размер не проверяется. |
| HTTP 200 содержит синтетический отказ `data.biz_code: 1` | **Провал в RU и EN.** После перезагрузки новый чат уже активен, снимок помечен применённым и привязка записана. Положительный HTTP-статус используется как подтверждение до проверки результата сервиса. |

При параллельном повторном прогоне в двух контрольных сценариях уведомление о подключённой памяти не появилось за 5 секунд. Первый полный прогон их прошёл. Последовательная перепроверка дала 8 проходов и 2 ожидаемых падения для отказа внутри HTTP 200. Причина двух таймаутов параллельного прогона пока не установлена.

Воспроизведение на распакованном архиве RP357:

```powershell
npx playwright test -c playwright.extension.config.ts continuation-chain-runtime.spec.ts -g 'saved-memory' --workers=1
```

В версии RP357 два сценария с отказом внутри HTTP 200 выявили ошибку хранилища. Текущие тесты RP358 проверяют сохранение прежней привязки. Затем нужно ограничить длину итогового отправляемого текста, сохраняя реплику пользователя. Кнопка переноса сейчас находится на странице исходного чата, поэтому нужен отдельный тест на случай, когда этот URL перенаправляет на главную и расширение теряет исходный ID.

Проверена сборка RP356 (`a1716cd`): каталог Chromium побайтово совпадал с архивом выпуска. Браузерные прогоны использовали отдельные профили Edge и локальные ответы на запросы к DeepSeek. Число 40 000 и HTTP-коды — параметры стенда, а не подтверждённый контракт DeepSeek. Живой аккаунт и личный лор не использовались.

| Сценарий | Что делает RP356 |
| --- | --- |
| История старого чата читается, отправка служебного запроса возвращает 403 | Штатный перенос останавливается на проверке памяти. Новый чат и снимок переноса не создаются. Сохранённая запись памяти и привязка игры остаются на месте. |
| Первый запрос в новом чате возвращает 429 после смены URL | Отправка не дублируется. Снимок переноса остаётся неприменённым; активным остаётся старый чат. |
| Итоговый текст из реплики, памяти и служебного разделителя: 39 999 / 40 000 / 40 001 символ | Все три запроса отправляются по одному разу с исходной репликой. Стенд отклоняет последний (413): предварительной проверки этого порога в RP356 нет. |
| Служебный запрос возвращает 403, 413 или 429 | Транспорт сообщает об отказе один раз и передаёт ответ браузеру. Автоматического повтора нет. |
| В чистом чате вручную выбран тот же мир | Сохранённая запись мира подключается к первым двум репликам и после перезагрузки (fetch и XHR, RU/EN). Этот сценарий не восстанавливает отсутствующую последнюю сцену. |

Результат: TypeScript без ошибок; 200 тестов Vitest прошли в 10 выбранных файлах на Node 24. В Edge прошли 22 сценария переноса и 4 сценария ручного подключения мира (RU/EN). Браузерные сценарии воспроизводятся после сборки Chromium:

```powershell
npx playwright test -c playwright.extension.config.ts continuation-chain-runtime.spec.ts --workers=3
npx playwright test -c playwright.extension.config.ts new-chat-memory-runtime.spec.ts -g 'memory clean/' --workers=2
```

## Следующая работа

1. Проверить и реализовать явное продолжение из локальной памяти без запроса в старый чат. Показать, до какого момента есть сохранённые данные, и не выдавать старую сводку за последнюю сцену. Переключать активный чат только после подтверждённой отправки в новом.
2. Проверять длину итогового текста перед отправкой с запасом до наблюдаемого порога; при нехватке места сначала убрать необязательную память или объяснить, что мешает. Не обрезать реплику пользователя. Учесть обычный ввод и служебные запросы (сводка, подготовка анкет, сброс).
3. На тестовом аккаунте отдельно подтвердить вид отказа (HTTP, ошибка внутри успешного HTTP-ответа или заблокированный редактор). Не принимать числовой порог или срок простоя за универсальное правило.

Код расширения и архивы на этапе этой проверки не менялись. Реализация резервного переноса описана в [RP357](RP357-SAVED-MEMORY-CONTINUATION-20261116.md).
