## Фоновая отрицательная проверка — причина теперь доказана

Первый дополнительный New chat был открыт инструментом в tab680, которая
оказалась фоновой. Запрос получил точный RP333 warning:

```json
{"stage":"navigation","code":"story-binding-conflict","detail":"activation-tab-inactive","elapsedMs":344}
```

Чат `3480fdd1-c1dd-43ba-9dbb-abf5c6313479` не стал writer общей игры;
его ответ пользователь остановил. Это **отрицательный результат**, не успешная
первая отправка и не пропуск, замаскированный повтором. Guard не ослабляли.
Разрешённый fail-open отправил запрос без памяти; не включали strict mode.

Пользователь явно выбрал нужный чат и прислал screenshot. Новый inventory
показал tab770; использовали её, а не cached680. Пояснение: получение tab handle
не активирует вкладку. После ручного выбора всегда заново читать inventory;
одинаковый URL/заголовок не подтверждает foreground.

**Нельзя задним числом приписывать этой причине все старые RP332 отказы**:
у них не было detail. В RP334 основной отказ больше не воспроизвёлся; изменение
RP333 уточняло диагностику и не меняло условия guard.

## Доказательства и пределы

- `benchmarks/rp334-verification.json` — результаты/границы.
- `benchmarks/rp334-live-replies.json` — все восемь ответов и два clean-контроля,
  только синтетическая история.
- `benchmarks/rp334-live-eight-passed-20261019.png` — гипотеза осталась гипотезой.
- `benchmarks/rp334-clean-first-passed-20261019.png` — первый запрос нового чата.
- `benchmarks/rp334-clean-after-reload-passed-20261019.png` — следующий запрос после reload.
- Полный рабочий прогресс: локальный `.output/rp334-live-progress.json`.

Восемь вопросов заданы последовательно в **одном** чате: последующие ответы
могут опираться на предыдущие сообщения и скрытый контекст прошлых запросов.
Это не восемь независимых blank-context retrieval тестов. Дополнительный
первый запрос пустого чата проверяет этот разрыв отдельно, но только на nora.
Панель показывала preview, отдельной квитанции actual POST не было. Независимый
аудит сетевого payload и DB здесь не проводился; UI/ответы не выдаём за него.

Исходные80 повторов RP330 остаются четырьмя ходами, а не80 сохранёнными
role-seeded фактами индекса. Большой сохранённый индекс/составные действия RP325
и RP-08 replay **не закрыты**. Личный Firefox и автоматизированные31 шага меню
также не проверяли. Меню не открывали из-за известного about:srcdoc ограничения.

## Передача дальше

копия уже обновлена и живой повтор прошёл. При новом реальном отказе сначала
читать свежий RP333 detail; не ослаблять foreground guard ради автоматизации.
