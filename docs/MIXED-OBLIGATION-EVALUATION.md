# RP289 Проверка памяти разных обязательств

Протокол фиксируется до первого запуска игрового компилятора на новом наборе. Проверяется неизменённый RP288: найдёт ли он полные принятые источники для доставки, ремонта, оплаты, сопровождения и неразглашения, не смешивая разные работы и разрешения. Исправлений runtime по ходу замера не будет.

## Новые истории и ожидаемые записи

Пекарня, ледниковая экспедиция, планетарий; по четыре действующих лица, RU/EN. Тексты и gold написаны заново без импорта старых corpora, matcher, scorer или результатов. Это agent-authored synthetic accepted-memory audit, а не слепой внешний тест или роман, сыгранный живым DeepSeek. Общая структура обязательств, переводы и повторяемый фон коррелируют;96 запросов не равны96 независимым историям. Проценты разных наборов нельзя трактовать как рост качества модели.

В каждой истории: обещанная доставка a0 и её условие доступа a1, новое место приёма a2, подготовка без выполнения a3; ремонт другой похожей вещи b0–b2; выполненная оплата c1/c2; отменённое сопровождение d1/d2; действующее обещание не разглашать сведения e0. aOld — устаревший destination claim, c0/d0 — superseded открытые задачи. Эти три записи запрещены в текущей передаче. Все обязательства имеют отдельные task keys и исторические роли; подготовка вещи не подтверждает доставку, разрешение перевезти/починить не разрешает раскрытие секрета.

Gold записан вручную: delivery/paraphrase/proved-reference требуют a0–a3, repair — b0–b2, two-jobs — их объединение, payment — c1/c2, cancelled escort — d1/d2, secrecy — e0. Наличие достаточного общего бюджета16000 является условием scored запросов; пропуски при низком бюджете учитываются отдельно. Gold по recall не присваивается ложным/неопределённым ссылкам.

## Разделение случаев

84 main = 3 сюжета × 2 языка × 14 форм, каждая за960 фоновыми сценами.48 scored: именованная доставка, перефразировка, ремонт, две работы, завершённая оплата, отменённое сопровождение, секрет, короткая ссылка с exact accepted bridge.36 controls: без bridge, ложный bridge только в raw recent, два самостоятельных упоминания общих префиксов, чужой владелец, несуществующая вещь, неизвестное raw продолжение после принятого bridge.

Ещё6 scored scale запросов двух работ за320/1800/6000 сценами, по3 сюжета RU/EN. Ещё6 budget probes900/2200/5000, исключены из semantic recall. Итого96 inputs,54 scored/36 controls/6 budget;42 main inputs с короткими/неподтверждёнными ссылками требуют unverified и explicit reference guard. Не оценивать все controls как exact historical output: на новом наборе прежнего результата ещё нет.

## Что измеряется отдельно

1. Полнота: все требуемые gold records целиком, missing records и семейства/языки. Содержательное условие из отдельной записи нельзя считать найденным по одному заголовку задачи. Дополнительные настоящие кандидаты не означают подмену владельца; их состав публикуется.
2. Целостность: text/quote/kind/task/claim, source roles и revision IDs/episode/period, persistent статус, отсутствие superseded/выдуманных/повторных записей, неизменность исходного input/canon/draft. Реальный formatter/decoder и полный added-context meter обязательны.
3. Неопределённость:42 short/reference controls ожидают unverified и guard даже при наличии нескольких полных кандидатов. Scored missing с coverage complete — отдельный false-complete относительно gold; UI complete не является доказательством смыслового понимания. Это не проверка фактического ответа модели.
4. Cold/warm: повтор с клонированным input и тем же GameSearchIndex должен давать идентичный output/coverage. Times/RSS относятся к harness вместе с обработкой synthetic данных, не к скорости живого браузера.
5. Бюджет: optional output не выходит за лимит, mandatory overflow отдельно; никакой обрезки условий/цитат или изменения канона. Бюджет — локальная оценка добавленного блока, не свободное окно native DeepSeek.

## Порядок и сохранность

`node scripts/story-search-mixed-obligation-audit.mjs --freeze` валидирует facts/seeds/source IDs/уникальность/gold и counts, затем пишет manifest с wx. Fingerprints включают ВСЕ src TS/TSX, новый fixture, runner, этот protocol и общий digest utility; EOL нормализуются только для portable fingerprints. Compiler не импортируется/не вызывается в этой фазе. `--evaluate` в другом процессе сначала сверяет manifest/input/gold/runtime, запрещает существующие report/seal и лишь затем импортирует compiler.

Первый report и SHA256 seal сохраняются неизменными, даже при провале всех scored запросов. Найденные потери/ошибки уверенности становятся задачей следующего этапа; новый fix потребует отдельного seen report, не переписывания gold/первого результата. Старые RP283/RP287 reports/seals тоже не меняются.

Перед первым compiler execution обнаружена только ошибка provenance в переиспользованном harness: первый manifest хешировал прежний runner вместо нового. Initial baseline и точный preflight runner snapshot сохранены, evaluation ещё не запускался. Отдельный v2 baseline регистрирует правильный собственный runner и этот уточнённый protocol; input/gold/rows и все runtime fingerprints должны совпасть с initial. Это не повторная оценка/подгонка по результату: первого результата ещё нет. Рабочий baseline для evaluation — `story-mixed-obligation-audit-v2-baseline.json`.

Проверка не использует личный лор, браузер, аккаунт, API или модель. Runtime/UI/storage/settings не меняются; текущие E5/MMR не интегрируются. Source ZIP исключает tests, поэтому для повторения нужен полный Git checkout и совместимый Node runtime.
